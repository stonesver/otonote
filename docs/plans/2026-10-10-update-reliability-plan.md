# 版本更新可靠性与发布运维改造计划

状态：首批实现已通过 PR #71（Worker 热修）、#74（Global 状态清单）和 #75（磁盘维护）合并，实际运行验收单独记录。其余章节保留为后续改造方案，不代表全部能力已经上线。补充现有 R2 更新性能方案，不替换已完成的共享媒体、CAS 去重、无变化门禁和云端解码能力。具体运行版本、账号配置、实测明细与原始报告保留在仓库外。

## 目标与约束

- 使用现有网站服务器、GitHub Actions 和 Cloudflare，不增加常驻生产服务器。
- Actions 承担下载、解码、转换与生产；网站服务器承担交付、预渲染和既有轻量服务。先以实测决定是否调整预渲染位置。
- 客户端更新、资源热更新、网页发布、计算规则更新、账号采集分别建模；不能把“资源下载成功”当成所有功能已更新。
- 保留签名、摘要、解码结果验证和发布门禁。失败时保留上一个可用版本，能够看见故障阶段和内容陈旧程度。
- 本计划不授权生产部署、删除、切换指针、账号登录或压测；实施时按具体工作包确认上线范围。

## 目标流程

```text
轻量发现客户端/资源变化
  → 固化候选版本与证据
  → 恢复必要状态、验证客户端与解码器绑定
  → 增量解码/转换/派生数据
  → 功能兼容性与完整性检查
  → 上传不可变内容、保存可恢复状态
  → 校验发布条件、晋级公共内容
  → 网站预渲染与交付核对
  → 核对用户可见版本、采集新鲜度和错误指标
```

每阶段保存输入摘要、代码/工具版本、输出摘要、耗时与失败原因。重试仅复用输入与契约仍一致的产物。已有晋级机制与双服交叉引用应当复用，不另造一套相互竞争的发布指针。

## 第一批：解除已知阻塞

### A. 先归并线上热修与源码

范围：`deploy/r2_content_gateway.mjs`、相关 Worker 配置模板、`site/tests/r2-content-gateway.test.mjs`。

1. 对比当前线上版本、热修工作区与主分支，归并缓存记账修复和已验证的缓存设置；记录提交、部署版本和验收结果。
2. 部署清单明确区分程序版本、路由配置和缓存设置，防止后续正常发布覆盖热修。
3. 验证同键替换的缓存容量记账、淘汰、Range、共享媒体、指针和内部路径。

验收：可由审阅后的源码重建线上行为；静态资源交付正常，动态指针保持新鲜，内部材料不可公开访问。上线前保存原 Worker 版本和配置用于回退。

### B. 修复私有状态清单膨胀

范围：`tools/r2_state.py`、`tools/global_update.py`、`tools/current_client.py`、现有保留策略模块、`.github/workflows/content-r2.yml`。

1. 加入只读盘点：按用途区分当前资源、历史资源、客户端、可信解码基线、缓存、临时文件；同时输出路径数、逻辑大小、唯一对象大小和预计清单大小。
2. 计算“下一次从空 runner 恢复并完成更新”所需的完整引用集合，而不是递归收集所有历史生产目录。保留当前输入、可靠回退、被解码器绑定引用的旧客户端/材料及跨阶段依赖。
3. 将历史归档和热恢复工作集分开。第一步仅缩小新清单及恢复范围，不立即删除远端历史对象；复用现有 JP 保留、CAS 和恢复复用机制。
4. 在能估算时提前报告预算，checkpoint 前再次精确校验。建议以清单上限的 80% 预警；接近上限时阻止昂贵生产前的可预见失败，但对新产物仍保留最终硬校验。
5. 修复失败后的空结果解析：保留首个实际错误，清楚区分上传、checkpoint 和晋级，不能用二次 JSON 错误覆盖根因。
6. 收缩后仍不足，再设计可向后兼容的分片索引或压缩格式；不以单纯调大上限代替引用与保留治理。

验收：合成历史目录不会进入当前工作集；当前/回退/可信解码基线引用完整；摘要损坏与缺失引用会拒绝晋级；从空 runner 恢复、完成一次候选生产和下一次无变化检查均通过。先用私有候选命名空间验证，不改现有 current。

验证入口：`tests/test_r2_state.py`、`tests/test_r2_state_reuse.py`、`tests/test_update_retention.py`、`tests/test_jp_state_retention.py`、`tests/test_current_client_upgrade.py`，并按改动补充行为测试。

回退：旧读取协议继续可用，保留旧 manifest 和对象；候选失败不推进状态或公共指针。已上传不可变对象可保留，不强行恢复或删除整桶。

### C. 网站磁盘治理

范围：`tools/operations.py`、预渲染发布与安装流程、相应运维模板。

1. 先生成只读去重/保留方案，基于设备、inode、硬链接数量和引用关系估算真正可回收字节。复用已有 plan/apply 工具。
2. 保护 current、previous、双服交叉引用、进行中的安装、回滚代码、浏览器仍可能请求的旧资源；HTML 和不可变资源采用不同保留期限。
3. 先执行可验证的重复载荷去重，再评估过期安装包、失败暂存和历史版本清理。清理必须使用可审阅清单，不能按目录日期或“只留两个版本”粗删。
4. 增加全流程磁盘预算：下载、展开、构建、待晋级和回退期间的峰值都计入，禁止并发任务各自判断空间够用却一起耗尽。
5. 增加保留与日志轮转的周期任务，记录回收量、受保护集合和失败原因。避免高峰期全树扫描与哈希。

验收：执行前后页面/媒体摘要与引用检查通过，现用版本和回退版本可用。建议运维目标为至少 8 GiB 空闲，并且覆盖实测阶段峰值和恢复余量；若无法满足，调整工作集/发布方式或评估原实例扩盘，不把未验证的“预计回收”当成已释放空间。

## 第二批：缩短更新路径

### D. 轻量探测与调度

范围：`tools/r2_production_gate.py`、客户端/资源探测入口、工作流。

1. 保留已经可跳过重生产的无变化分支。先量化探测镜像拉取、依赖启动和远程请求，确有收益再拆分轻量镜像/独立入口。
2. 分开记录上游维护、探测失败、客户端变化、资源版本变化及代码变化，避免将任何失败转成“无更新”。
3. 常态可先评估 15 分钟探测，已知活动窗口临时提高频率；生产保持同服串行，以候选版本合并重复触发。不能取消正在上传或晋级的任务。
4. GitHub 定时任务可能延迟或丢弃，记录应运行/实际运行时间和连续漏跑。只有实测时效不达标时，再评估外部轻量定时触发器及最小权限凭据；无需新增常驻生产机。
5. 内容生产触发指纹按真实依赖收敛，不能因为不相关工具变动恢复整套素材，也不能漏掉评分规则、转换器或配置契约变化。

验收：无变化路径不恢复全量状态、不运行生产、不上传、不晋级；热更新与客户端更新都能触发；维护结束后可自动恢复。探测时效以实际分布验收，不将 cron 间隔当成时效保证。

### E. 有变化时的恢复、转换和 checkpoint

1. 基于 B 的工作集选择恢复内容；在逐文件 GET、分片清单、小文件打包之间先做代表性样本对照，衡量请求数、CPU、带宽、内存、临时磁盘和重试代价后决定格式。
2. 跨运行缓存键包含原始资源摘要、转换器版本、参数和必要依赖；同一版本重试可复用，不同规则变化必须失效。复用现有共享媒体与已验证目录，避免重复实现。
3. 区分解码、图像、音频、场景和派生数据耗时；按资源类型识别强制重复工作的来源。受 runner 内存和带宽约束设置并发，不直接调到最大。
4. checkpoint 尽量复用已验证索引，不重复扫描/读回所有无变化内容；保留完整性和原子提交保证。
5. 预渲染按受影响区域及真实交叉引用重建；评估周期“无变化”检查重复哈希整个发布树的成本，再考虑基于不可变标识的快速路径。

验收：使用固定输入比较冷恢复、暖恢复、少量热更新、新客户端四种场景；产物内容一致，缺失/损坏可检出。分别给出每阶段时间、峰值 RAM/磁盘、R2 GET/PUT 次数和复用率，再确定总时延目标；不把一次小更新的成绩承诺给所有大版本。

## 第三批：高峰交付与功能一致性

### F. Worker/CDN 与页面请求预算

1. 在现有缓存修复基础上区分：到达边缘的请求、执行 Worker 的请求、R2 读取、CPU 超限和计费请求。核对实际套餐与 UTC 计费窗口。
2. 统计高峰按分钟的请求、错误类型、执行 CPU、缓存命中、R2 请求和热点路径，找出一次打开页面/工具产生的请求扇出。
3. 保持不可变媒体长缓存、mutable 指针短缓存或 no-store、鉴权和个人数据不可公共缓存。检查缓存键覆盖地区、语言、查询参数和 Range 语义。
4. 若仍需要减少 Worker 执行，评估将明确允许公开的不可变媒体通过独立公共桶/域名交付。先证明路由及访问控制边界，不直接把含私有对象的现有桶公开。
5. 为公开 HTML 评估 30–60 秒边缘缓存与后台更新，明确版本切换和陈旧上限；先小范围验证，不对登录/个人数据页面套用。
6. 调查大页面和重复数据请求；测压缩传输量、浏览器解析耗时、首屏资源和计算器加载，再决定拆分数据、按需加载或去重。保持内容摘要稳定，避免仅因 releaseId 变化让未变素材全部换 URL；验证 Live2D 等相对路径资源。

验收：缓存命中不执行重逻辑，不产生错误的跨地区/跨用户响应；新发布在承诺时限内可见；旧页面资源在兼容窗口内仍可读。以隔离环境回放代表性访问模型，按阶梯提升并发，再做限定线上抽查；不对现网直接做突发压测。

### G. 功能更新矩阵与用户可见状态

| 能力 | 版本变化后应自动发生 | 仍须独立验证 |
| --- | --- | --- |
| 活动、卡片、技能目录 | 拉取新数据，建立引用，重建对应页面 | 新枚举、未知结构、关联素材完整性 |
| 计算器/评分 | 采用正确地区和资源版本的数据 | 新机制、技能语义和评分规则是否被代码支持 |
| 榜单/周期采集 | 刷新已支持客户端信息，重试暂时维护 | 协议变化、账号状态、采集时间和有效样本 |
| 成长/账号查询 | 错误分类并提供明确状态 | 登录与风控、业务参数、版本兼容，不能等同静态发布 |
| 客户端解码 | 云端下载、校验、绑定和解码已支持材料 | 未知加密变化和无法验证的新映射须停止并通知 |

1. 使用地区、客户端版本、资源版本、生成时间和能力检查结果形成发布记录。
2. 区分阻止晋级的必需检查与允许降级的可选功能；部分功能未知时保留上一可用结果并明确陈旧状态，不能展示空结果当成功。
3. 功能级抽查必须覆盖新活动、新卡、至少一种新技能样例、计算器输入版本、采集最新成功时间。进程退出码为 0 不等于业务数据新鲜。
4. 全球服自动绑定与日服固定版本升级分别定义验收。对未知加密变化保留受审适配流程，不能承诺永远无需人工。
5. 完成一次“空云端 runner，无本机挂载、无手工拷贝”的端到端验收，随后验证无变化运行。所需可信基线和私有配置都通过受控云端存储恢复。

回归入口包括现有客户端升级、解码器、生产门禁、内容保留、预渲染发布/晋级测试；新增测试针对失效行为和跨阶段契约，不重复断言实现细节。

### H. 告警与故障定位

最少记录以下指标：最新发现版本、最新成功生产/发布/交付版本、各阶段耗时、连续失败、采集新鲜度、清单预算、磁盘峰值、Worker 错误与请求预算。运行链接与发布记录相互关联。

告警分开处理维护等待、探测失联、未知客户端、状态保存失败、交付版本落后、动态服务异常及容量不足。采用持续时间和恢复通知避免刷屏；阈值先按实测基线制定。历史窗口按统一时区对齐，同时保留 UTC 计费口径。

## 实施顺序与交付门槛

建议拆成 8–10 个可独立审查、可回退的小 PR：

1. 归并 Worker 热修与发布版本记录（A）。
2. 状态预算报告、明确失败阶段及空结果修复（B 前半）。
3. Global 当前工作集与保留引用闭包（B 后半）。
4. 服务器去重/保留方案及预算门禁（C）；实际清理单独审阅。
5. 探测调度与依赖指纹（D）。
6. 增量恢复、转换与 checkpoint 优化（E，必要时拆分）。
7. 边缘请求预算与页面交付改进（F）。
8. 功能版本矩阵、云端独立验收与告警（G/H，可拆分）。

A、B、C 最优先；E 依赖 B。F 的观测可提前，缓存策略变更在现有热修归并之后。已有并行开发中的功能修复应归并成果，不另行实现冲突版本。

每个工作包依次交付：改动和回退方案 → 有针对性的本地/CI 验证 → 私有候选验收 → 明确范围的上线 → 用户可见结果验证。首轮验收结束再根据数据决定是否需要外部调度、存储扩容或进一步拆分，不能先以购买新服务器作为前提。

## 平台约束依据

- GitHub 定时工作流具有延迟/丢弃可能，最短间隔不等于执行时效：[schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。
- Workers Cache、Worker 执行与计费口径需要分别核对：[Workers Cache](https://developers.cloudflare.com/workers/cache/)、[计费文档](https://developers.cloudflare.com/workers/platform/pricing/)、[执行指标查询](https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-workers-metrics/)。
- R2 自定义域名与公共访问必须明确对象边界：[R2 公共桶文档](https://developers.cloudflare.com/r2/buckets/public-buckets/)。
