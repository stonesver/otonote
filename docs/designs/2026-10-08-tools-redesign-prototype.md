# OtoNote 工具工作台 V2：功能划分与内部交互

> 2026-10-09 更新：内部布局已收敛为 A＋B 融合，当前原型与验证见 [V3 设计稿](2026-10-09-tools-workbench-v3.md)。本稿保留功能划分与 V2 走查记录。

2026-10-08。此稿取代 V1。用户确认工作台的大方向，要求重新设计内部功能、交互和排版，并明确歌曲排行榜保持独立。

## 已确定的边界

- **歌曲排行榜独立**：保持 `/tools/song-ranking/` 与工具目录、侧栏中的独立入口。它的统一基准、效率与达档综合力不纳入个人估分页签。
- **工作台方向保留**：三种新原型都遵守工作台框架，只比较内部条件与结果的组织。
- **素材检索删除**：上一轮已删除本地专属页面、模块、入口及文案，相关 21 项测试通过。尚未发布。
- 本轮修改设计实验和设计稿，正式计算工具尚未重构。

## 1. 上一版内部结构的问题

1. “出分、稳定、综合力、培养试用”被放成一组大卡片，但前面三者是比较目标，后者是卡牌假设。同一个用户可能需要“允许培养＋最低分优先”，不能把它们设计成互斥目标。
2. 配队中的“当前队伍”与估分中的“当前队伍”含义不同。配队要搜索候选，估分要固定编成，上一版都叫卡片来源，容易混淆。
3. 手动更换配对被塞进“管理卡库”。持有、养成管理与编辑五组编成是两项不同操作。
4. 页面顶部的目标卡、上下文条、任务导航占用过多高度。新手知道选了什么，仍难同时看见实际输入和结果。
5. 没有把“原有队伍、推荐候选、已应用队伍”充分分开，导致操作语义含混。
6. 结果排序和判档依据属于比较结果的操作，不应与必须重新计算的输入混在一起。

## 2. 新的功能归属

| 模块 | 做什么 | 不依赖什么 | 放在哪里 |
| --- | --- | --- | --- |
| 我的卡库与养成 | 管理持有、实际等级／突破／觉醒、导入与账号加成 | 不要求先选歌 | 独立管理页；任务内“管理卡库”入口 |
| 当前队伍编辑 | 五组成员／留影配对、队长、固定编成草稿 | 不运行配队搜索 | 工作台顶部摘要 → 独立编辑面板 |
| 配队推荐 | 在指定卡牌与假设中寻找编成，输出可比较候选 | 不覆盖当前队伍 | 配队工作台 |
| 单曲估分 | 固定队伍、固定谱面，估算分数范围与技能贡献 | 不搜索其他队伍 | 估分与选曲的“单曲估分” |
| 队伍选曲 | 固定队伍，比较多首谱面 AP 档位 | 不重新推荐编成 | 估分与选曲的“队伍选曲” |
| 活动速算 | 使用游戏内已知加成、评分和消耗估算奖励 | 无需卡库或歌曲 | 活动收益的“已有加成速算” |
| 活动完整规划 | 用卡库比较编成、歌曲与预算内收益 | 需确认活动、范围和预算 | 活动收益的“卡库完整规划” |
| 歌曲排行榜 | 使用统一基准比较歌曲 | 不读取个人队伍 | 独立页面与独立目录入口 |

推荐、估分、活动可以互相带入必要数据。联动不改变各模块的职责。

## 3. 配队：四组条件，三个层次的操作

### 条件区

| 分组 | 具体控件 | 显隐和作用 |
| --- | --- | --- |
| 推荐目标 | 平均分／最低分／最高分／综合力 | 综合力隐藏歌曲、判定和技能顺序条件；其他目标需要谱面 |
| 卡片与养成 | 我的卡库／全部卡牌参考 | 卡库使用实际持有；全部参考使用参考养成，不修改持有 |
| 养成假设 | 保持实际养成／允许培养；最多培养几张 | 只在我的卡库下呈现；培养不是推荐目标，可和任一目标组合 |
| 临时试用 | 按需加入未拥有卡牌 | 在卡片与养成下展开；与培养可组合，结果同时标记两项假设 |
| 歌曲与演出 | 歌曲＋难度选择器、普通／激奏、发挥预设 | 选择后只显示谱面摘要；精细发挥和账号加成按需展开 |
| 编成限制 | 必须保留的成员／留影／配对；属性、乐队等限制 | 按需展开；利用当前队伍作为固定对象，不把当前队伍伪装成完整卡库 |

最低分表示特定假设下的技能顺序低值；激奏可能是样本低值。不能将它写成保证达档或实打成功率。最高分同样保留样本／理论范围的说明。

原型已有四种目标、两种卡牌范围、培养张数、临时试用、配对锁定选择。约束只进入样例状态快照，尚未接入真实搜索。

### 顶部当前队伍

摘要只承担三件事：说明当前使用哪队、标记实际／参考／培养／试用来源、打开编成编辑。

推荐结果生成后仍是候选。点击“应用此编成”才替换当前队伍；“用此编成选曲”明确应用这一候选并进入选曲。修改推荐目标不会改变当前队伍。

### 推荐结果

显示顺序：候选方案切换 → 主指标与范围 → 五组配对及队长 → 谱面与养成假设 → 应用／选曲／对照当前队伍 → 配对原因与搜索范围。

正式候选应按真实差异组织，比如更高分、少培养、满足固定角色，不能对完全相同的编成重复贴标签。原型提供两份有不同留影配对和队长的样例，验证切换与应用。

## 4. 手动配对：独立编辑，确认才应用

1. 从顶部“编辑当前队伍”打开面板。还没有队伍时，允许选择或创建手动草稿。
2. 五组编成始终显示；点位置明确当前正在编辑哪一组。
3. 在该位置切换“更换成员／更换留影”，候选列表只负责选择卡片。
4. “将此位置设为队长”独立于选卡。
5. 草稿修改留在面板内；“取消修改”或关闭不替换当前队伍。
6. 底部固定显示“取消修改／应用编辑后的队伍”。长卡片列表滚动时也能确认。
7. 应用后标记旧计算结果过期；不改变卡库持有和实际养成。

正式版需要搜索、乐队／角色／属性／技能过滤、卡面和技能预览；这些沿用现有选卡能力。固定同一卡或配对的约束规则必须由真实数据验证。原型使用小样例库，重复选择已有成员或留影时交换位置，避免同一张样例卡重复占用两个位置；未验证所有游戏编成限制。

手机采用两列配对。每一组内部左侧成员、右侧姓名与完整留影名称，第五组保留，不将五个位置挤成五条窄列。

## 5. 估分与选曲：只保留两个页签

### 单曲估分

条件：固定队伍来源 → 谱面 → 模式与发挥。队伍来源是当前队伍、保存的队伍、参考队伍，不使用“全部卡库”这个会暗示搜索的名称。

结果：分数与范围、档位、实际采用的发挥／谱面／演出条件、技能覆盖，再进入贡献和逐音符明细。换队／曲／发挥后重算；修改结果排序不影响计算。

### 队伍选曲

条件：固定队伍 → 普通／挑战范围及活动 → 难度／等级上限。AP、满生命、无辅助假设保持可见。

结果区承载平均／最低／最高判档依据和档位／短歌／估分排序。两者使用已算结果，不发起新计算。每行显示曲名、谱面、时长、档位、分数；正式接入补充离下一档差距及部分失败提示。

选中一行带入谱面和这支固定队伍，进入单曲估分；需要独立计算。对临时试用或培养编成，来源标签继续保留。

原型演示两个页签、固定来源、范围、结果筛选与行联动；多曲普通／挑战选择及真实计算尚未接入。

### 排行榜保持独立

保留当前排行榜的得分、时长效率、达档综合力和统一口径。允许单向“配这首歌”的联动。原型单独提供 `task=ranking`，不与个人结果共享排序或难度；正式 `/tools/song-ranking/` 不更改归属。

## 6. 活动内部也按“输入”和“比较结果”划分

- 速算页签只呈现已知加成、稳定评分、演出类型与消耗。无队伍摘要和选歌要求；修改后直接更新奖励。
- 完整规划呈现卡片与养成假设、活动、优先奖励、预算、歌曲能力上限、普通与挑战范围。
- 速算记住方案后，在相同活动、演出类型和消耗下比较奖励差；改变口径时说明不可直接比较。
- 完整结果先给预算总收益，再展示普通编成、歌曲、消耗与次数，接着展示独立挑战编成和挑战 pt 收支。
- 两种奖励分别显示；剩余挑战 pt 不折算成已到账收益。应用普通与挑战编成分别操作。
- 有队伍不触发速算自动转完整规划。切页签保留草稿，新任务仍确认自己的条件。

原型速算使用普通演出样例表，完整规划使用两阶段样例快照。真实活动选择、挑战速算、挑战队伍编辑、次数优化及正式保存不在本原型中。完整阶段只有示例布局，不宣称找到最优收益。

## 7. 内部排版的三种验证

三个版本都属于已选定的工作台方向，旧版 B 分步向导、C 编成台不再作为候选。

| 版本 | 内部结构 | 收益与成本 |
| --- | --- | --- |
| A：条件与结果并排 | 左侧窄条件栏，右侧宽结果；计算操作在结果上方 | 条件与结果可同时核对，适合反复调参；手机上下排列 |
| B：结果优先、条件侧栏 | 主区留给候选与比较；按钮打开条件侧栏 | 结果更宽；调整条件暂时遮挡结果，不适合频繁对照字段 |
| C：顶部条件、下方结果 | 条件在顶部横向组织，结果全宽 | 适合长结果表与阶段方案；加入培养／试用后条件高度可能增长 |

当前建议配队和速算先用 A；多曲表可借鉴 C 的全宽结果。B 保留为结果查看时的收起条件形式，而不是首次使用默认入口。最终可以按任务采用不同内部排版，不必所有工具统一一个列宽比例。

视觉继续使用 OtoNote 紫色操作、蓝色结果、冷灰工作区。顶部取消大片目标卡；目标用紧凑切换，卡片和输入分组使用边线分隔。养成来源贴在队伍及结果附近。

手机计算完成后定位到结果标题。编辑面板确认操作固定在底部。真实软键盘、触摸与屏幕阅读器仍需后续实机验收。

## 8. 状态与正式接入

正式模块应复用现有 `team-workspace-store.mjs`、`shared-team-workspace.mjs` 和 `team-planning-optimizer.mjs`；图谱检索与源码确认：规划目标、养成场景、发挥场景和约束已经是不同输入，UI 应反映这一点。

| 状态 | 界面反馈 |
| --- | --- |
| 卡库为空 | 在来源处说明，提供导入或参考入口 |
| 没有固定队伍 | 估分条件处要求选择；不自动运行推荐 |
| 缺少谱面 | 指向歌曲选择器 |
| 正在计算 | 显示过程与停止操作，保留输入 |
| 已取消 | 保留草稿与旧结果，说明是否有部分完成数据 |
| 条件已改 | 旧结果作为快照保留，禁用应用和跨工具动作 |
| 部分机制不支持／搜索未完整 | 解释具体缺口、采用范围和可继续操作 |
| 区服切换 | 隔离卡库、草稿与规则版本，恢复目标区服数据 |

正式结果保存条件签名，按相关条件精确失效。原型采取保守失效策略，多数输入变化会使既有样例结果过期；结果排序、判档依据、任务页签与独立榜单过滤不触发失效。这一简化不能直接复制进产品。

培养和试用只有规划快照；不能写入实际库存。生成结果不应用，应用也不标记试用卡为持有。

旧路径、语言／区服、队伍、歌曲、谱面与活动参数继续可用。先共享布局与队伍选择，再合并单曲与 AP 容器，排行榜独立保留。不要直接把样例脚本变成生产引擎。

## 10. 接下来正式实现的具体顺序

1. 先实现配队工作台 A 的完整链路：条件分组、歌曲摘要、独立队伍编辑、推荐与比较、显式应用、来源快照。接真实约束和规划引擎。
2. 验收培养＋任意推荐目标、试用＋培养组合，确认实际库存不变。补齐真实差异、培养清单及搜索范围说明。
3. 共享单曲与多曲估分布局，固定编成来源语义；保留 AP 普通／挑战条件与技能明细，歌曲排行榜独立。
4. 再完善速算与完整活动规划，真实奖励分别列出，普通／挑战队伍分别应用。
5. 以实际任务检查移动端队伍编辑、长名称、筛选、软键盘和结果定位。根据使用反馈决定是否默认折叠条件。

每一步交付一条可使用的完整流程；不先迁移所有页面再补交互。真实引擎接入后，用改版前后相同输入对照分数范围、档位和奖励，并检查旧链接参数。
