# 演出计分、激奏配队与养成方案完成报告

本报告对应[已确认设计](2026-10-04-performance-and-team-planning-design.md)，代码位于 `codex/performance-team-design`。功能在本地开发分支完成集成，尚未上线。

## 设计落实

| 阶段 | 已实现 | 审阅重点 |
| --- | --- | --- |
| 共用演出基础 | 普通与激奏共用玩家表现输入；明确逐事件回放；综合力、局内技能、模式奖励与活动收益分别处理；挑战与收益计算传递表现条件 | 同一队伍、同一原始操作能在配队与单曲计算中复核；活动加成不重复计入 |
| 卡片与养成场景 | 当前卡库、手选卡、参考卡与试用卡；独立保存实际和目标养成；指定培养范围与卡数；先提升允许培养的候选再搜索 | 未培养卡能进入候选；不修改卡库；未知养成与未知持有状态不会冒充实际；手填养成可比较同一队伍培养前后 |
| 玩家表现与激奏 | 理想、稳定、练习与明确输入；偏早偏晚、波动和难段；COMBO／LUCK／JUST任务、技能交互、对手与固定名次条件 | 换卡使用同一批原始操作；扩窗技能能影响有效判定；有对手与无对手的结果说明不同 |
| 多方向推荐与预设 | 冲分、稳定、段落竞争方向，重复方案合并；有限搜索与取消状态；目标预设恢复、重新导入后刷新；多歌曲预设池及按需技能详情 | 不把抽样最好分称为理论上限；不把较低样本分称为保底；换歌及刷新卡库后重新计算 |

页面以场景选择和少量预设为入口，详细设置按需展开。无卡库时可直接使用参考队伍或手选卡；养成计划保留培养目标，结果列出实际可比较范围。手机页面保留同样的操作路径。

## 机制依据与验证层次

[机制证据记录](2026-10-04-performance-mechanism-evidence.md)列出13项已发布激奏效果的实现依据，以及48个原生 ARM64 指令块对照用例。普通技能、COMBO最大连击、任务保护的消耗与判定转换均有专门测试。

这些证据用于核对具体逻辑，并不代表已完成真实客户端的全部事件顺序验收。当前仍保留以下边界：

- 时机输入使用已说明的判定模型，没有声称完整复刻触摸、长按调度；普通与激奏判定转换混用的部分事件顺序仍需真实客户端观察。
- 配队采用有限候选和抽样复核，不承诺穷举最优。默认限制培养组合和最终复核数量，取消或耗尽预算会在结果中显示。
- 未提供对手时，段落竞争方案比较任务表现，不预测胜率。提供对手后才按这些条件比较名次。
- 未知持有、缺失实际养成与参考养成分开处理；缺少真实材料背包时只列培养目标，不声称材料足够。

## 验证记录

最终提交的正式候选身份与验证回执单独保存在构建产物中，避免报告自引用改变提交身份。定向计算、页面与集成测试覆盖：

- 空卡库参考方案、部分卡库缺养成、单卡培养限制、弱卡培养后入队、取消与预算耗尽。
- 当前最佳队伍、计划队伍当前表现、目标表现分开比较；比较基线遵守相同筛选条件。
- 保存与恢复计划、卡库更新、旧预设缺失字段及另存往返、多曲池共用表现条件；综合力推荐保留发挥设置，最高／最低样本目标不在方向筛选时丢失。
- AP兼容、非AP回放、固定技能顺序、随机种子、扩窗与判定转换、任务计数及活动透传。

全量 Node 测试951项全部通过；类型检查660个文件，0错误、0警告（20项既有提示）。正式候选门禁的执行结果和源码身份见构建回执。Python全量测试运行898项：6项失败、46项错误、7项跳过；52项未通过均在变更前的 `3898f0b` 基线上复现，未发现本次新增失败。原因包括缺少可选依赖、私有数据与受限环境，不能把这一结果写成全量通过。正式候选所要求的Python交付门禁另行完整执行。

已做浏览器验收：无卡库普通参考配队、激奏多方向方案、保存两套队伍、两首歌预设池比较、技能详情、跳转单曲复算、英文入口及390像素手机布局；手选五成员和五留影、逐槽确认实际等级、仅培养一张卡，以及中途停止保留已算完的方案。激奏示例“壹雫空 EASY”在配队与单曲页均得到6,147,730.63分；不同方向显示各自条件，不保证第一。手选培养示例在停止后清楚显示仅将一张成员卡从Lv.10升至Lv.50，同队当前1,436,615.07分、目标1,607,740.8分，持有未知的账号基线保持空白。

## 建议审阅顺序

1. 配队页保持不导入卡库，选歌曲并生成参考方案，确认养成标签和取舍说明。
2. 手选卡并确认当前养成，选择只培养一张卡，对照目标和实际记录。
3. 切到激奏，改变发挥情景，检查冲分、稳定与段落竞争方案。
4. 保存两套方案，选择两首歌比较预设池；展开详情，再跳转单曲核对。
5. 对照机制证据与测试结果审阅底层，确认尚需真实客户端确认的边界。
