# 官方更新档案实施计划

状态：已获本地实施授权，M0–M7 的本地代码与验证已交付；M8 未执行。未获部署、启用归档、写入云端或清理真实数据授权。实际证据与结构调整见 [本地交付记录](../designs/2026-10-20-official-update-archive-local-validation.md)。

依据：[官方更新档案设计](../designs/2026-10-20-official-update-archive-design.md)。设计冻结于本地提交 `5a0e46b`，其中程序基线仍为 `2e6f3a2`；后续实施先重新核对当时主线与生产现状。

## 1. 交付目标与优先级

最高优先级是保持现有 Global、JP 北京时间 **09:00、14:00、19:00** 的网站更新可独立执行。归档默认关闭，功能与回归全部完成后，才在独立发布阶段逐服启用。

功能完成标准：

- 三个既有时点自动发现并保存普通新增/修改原件，不依赖管理员登录或逐批确认。
- 网站生产与归档使用独立 runner、区服锁和结果，允许重叠文件分别向官方下载，不增加下载搬运/协调机制。
- 双服共用 **2 GiB** 当前保有量，保留最近 **10 × 24 小时** 内发现的更新；先清理过期内容，总量不足再全局 FIFO，工作台可提交手动清理。
- 大版本/过大保存单元进入明确待选；小热更继续自动处理；自动待续、手动补存、清理和预览状态互不混淆。
- 现有 Our Notes 管理工作台增加 `#archive` 模块，支持查看、筛选、图片/文本/可支持音频预览、下载、补存和清理。

“现有更新不受影响”的可验证含义是：不改调度时点、生产准入/锁/发布语义，不引入归档完成依赖，不污染生产状态，不让归档争用已不足的执行资源。它不表示新增功能没有账户级开销。当前生产指纹覆盖整个工作流文件，首次接入可能触发原机制要求的完整恢复/生产，必须单独纳入上线验证，不能跳过。

## 2. 必须守住的生产边界

| 边界 | 实施要求 | 验证方式 |
| --- | --- | --- |
| 调度 | 仍只有 `0 1,6,11 * * *`，不增加轮询、清理 timer 或第二份 cron | 保留实际 selection 脚本测试，核对三个北京时间时点及外部 timer 未改变 |
| 生产 job | 原 `produce` 的区服开关、手动 region/mode、auto-promote、运行时和超时语义保持 | 对接入前后 job 配置与实际选择结果做差异核对 |
| 序列化 | 原 `content-r2-<region>`、`cancel-in-progress: false` 和跨服失败隔离保持 | 手动/定时选择矩阵与归档故障场景回归 |
| 工作区 | 归档不挂载可写生产目录，不复用生产 runner 的本地文件 | 用拒绝生产路径写入的测试替身验证；核对任务挂载、环境与命令 |
| 持久状态 | 归档不写生产 checkpoint、公开指针、生产运行回执或健康时间 | 测试存储适配器拒绝对应 key；对生产前后状态做实际核对 |
| 门禁 | 网站 unchanged 与归档待办分别判断，不把旧缺项送入生产完整恢复 | 保留轻量门禁与新补存组合回归，不修改门禁真值来适配归档 |
| 故障 | 归档超时、解析失败、FIFO 失败、存储满都不取消生产 | job 无互相 `needs`，不新增工作流级取消；模拟故障并记录两边结果 |
| 资源 | 在满足两服既有生产需要之后接纳归档 | 启用前取得账户/runner/网络/存储余量证据；不足则归档保持关闭 |
| 回退 | 优先只关闭归档开关，不取消整个工作流或回退生产数据 | 演练关闭后下一次生产仍正常、归档停止新工作 |

生产入口、传输、指纹、现有回执格式不是本功能默认改造范围。确有必要修改共享工具时，单列变更理由和回归，不能顺手重构。

## 3. 代码与交付范围

以下保留规划时的职责拆分；实际文件映射见本地交付记录，部分职责合并在同一深模块中。

归档主包放在 `backend/update_archive/`。现有源码发布允许 `backend/`，运行时包允许其中的 `.py`；当前生产指纹扫描 `tools/`、`analysis/crypto/`、共享计分及生产配置，未直接扫描该新包。这样归档专属修改不必新增生产指纹目录级豁免。

| 范围 | 拟定文件 | 职责 |
| --- | --- | --- |
| 模型与决策 | `backend/update_archive/models.py`、`diff.py`、`policy.py`、`config.py` | 固定身份、分来源基线、差异、状态机、预算与默认关闭配置 |
| 持久化 | `backend/update_archive/store.py`、`quota.py`、`retention.py` | 允许清单、不可变对象、账本/CAS、FIFO/到期/手动清理、墓碑与读取租约 |
| 来源接入 | `backend/update_archive/sources/global_source.py`、`jp_source.py`、`client_entries.py` | 官方版本/目录、最小可信材料、受限下载、客户端包清单 |
| 执行 | `backend/update_archive/requests.py`、`worker.py`、`receipts.py`、`__main__.py` | 请求队列、三次执行内的优先级与时间预算、恢复、独立回执 |
| 预览 | `backend/update_archive/previews.py` | 复用现有转换工具，生成有界图片、文本和支持音频结果 |
| 管理 API | `backend/admin/archive.py`；局部修改 `app.py`、`config.py` | 懒加载存储适配器、认证读取、补存与清理计划；不运行解包 |
| 管理前端 | `backend/admin/static/archive.mjs`；局部修改 `index.html`、`admin.mjs`、`admin.css` | 同一工作台模块，隔离样式/失败状态，轻量刷新、预览和下载 |
| 工作流/配置 | `.github/workflows/content-r2.yml`、`check.yml`，新增外置配置示例 | 最后接入默认关闭的归档 job，独立运行时与凭据作用域 |
| 交付/运维 | 独立归档依赖清单（如确需）、`deploy/admin/admin.example.json`、运维文档 | 固定运行时、最小权限、分阶段启用、清理及关闭回退 |

归档可单向调用已有经过验证的传输/解码工具，禁止生产代码反向导入归档包。新归档依赖不得通过更换生产镜像或放宽生产门禁获得。现有 Python 运行时包不包含管理静态资源，不能用运行时包校验通过替代管理页面实际交付验证。

## 7. M2：对象存储、双服 2 GiB 与清理

工作项：

- [x] 先实现注入式对象存储接口及内存/临时目录测试替身，再接私有 S3/R2；接口只接受验证后的归档 ID，拒绝生产指针和任意用户路径。
- [x] 不可变对象上传并完整读回后，才提交引用；同一档案内去重、不同区服物理副本分别计量。
- [x] 实现共同账本、条件提交、写入预留与 fencing。双服不各自计算可用空间，租约过期不等同于对象已删或预留可以无条件释放。
- [x] 64 MiB 控制预留包含在 2 GiB 内；约束控制换代峰值、最小基线和诊断大小。原件、预览、上下文、未引用对象及未完成上传均受同一上限约束。
- [x] 实现到期与 FIFO 计划：按首次入库时间跨服排序，以原件及专属派生结果为清理单元；按实际物理释放量继续推进，共享引用不重复计算释放。
- [x] 原件先在独立 runner 本地取得并校验，再申请/释放远端空间。单项连必要状态都无法容纳时先拒绝，不能先删空再报错。
- [x] 实现有界读取租约、`evicting` 状态、清理墓碑、幂等删除确认和中断恢复；提交时复核修订及过期，阻止迟到上传让已删内容复活。
- [x] 手动清理计划固定具体选择、修订、预计真正释放量和影响；确认后入共用队列，下一既有归档执行处理，不立即伪报已释放。
- [x] 已过期内容在读取时不可用；物理删除在下一次已有任务执行。仅记录模式仍维护生命周期，归档全关时如实显示无自动清理执行时点。

新增 `tests/test_update_archive_store.py`、`test_update_archive_quota.py`、`test_update_archive_retention.py`。

必须覆盖：双服同时抢最后额度；新旧控制对象同时存在；中途上传/删除失败；403 与真正不存在的区别；多引用 FIFO；读取中清理；清空后下一次普通新内容仍自动保存；人工补存不延长十天窗口；预览不能为自己主动踢掉旧原件。

完成标准：所有写入状态转换保持 `实际占用 + 在途预留 <= 2 GiB`，可在小容量合成样例下系统性验证，不需要上传 2 GiB 测试垃圾。

## 14. M8：启用前条件与逐服发布

### 14.1 本计划不自动执行的上线前核验

- 核对实际部署版本和当前两服原生调度、生产开关、固定镜像、生产回执及公开内容身份；本计划中的源码核对不能代替线上读数。
- 确认账户级 runner 并发与网络/存储请求余量足以保障两服既有生产后再运行归档；不能用归档抢到名额后退出当作容量保障。
- 配置最小生产材料只读权，以及归档根读写/删除权；管理服务只需档案读取和控制/请求写入。无论凭据如何提供，归档不得获得公开晋级入口。
- 验证独立运行时、官方双任务访问额度及归档 20 分钟预算；不足先保留关闭，不改变现有生产频率、并发或门槛。
- 所有真实归档验收对象、回执和清理状态进入共同 2 GiB 账本；不另建不计量的影子副本来规避上限。云端删除验证只针对明确标识的合成档案对象，不使用真实生产或历史素材演练。

### 14.2 分步接入

1. 在另行获批的发布范围内交付已验证源码与管理产物，归档执行开关保持全关闭。现有生产继续按三次原时点运行，不暂停它来验证归档。
2. 接入工作流的提交会改变现有生产指纹，允许原门禁要求的首轮完整恢复/生产；核对两服真实结果、回执和交付。不得伪造旧回执匹配新指纹，也不承诺手动 shadow 可以自动免除这次成本。
3. 等取得相同来源、有效新回执下的无变化检查，证明生产重新走轻量路径。若上游期间持续变化，则继续记录真实全路径原因，不能修改源版本让测试变绿。
4. 在容量证据和独立云端验证通过后，先只启用 Global 归档，策略设为仅记录建立基线；下一既有时点确认清单、状态、到期执行与生产独立。
5. Global 切为自动保存，等待实际新增内容或获批的有界验证，核对原件、读回、预览、工作台和共用容量。没有新内容不能宣称自动下载已验收。
6. JP 依次仅记录建基线、自动保存；分别核对日服可信客户端及出口配置，Global 不重新建基线。两服共同账本不得各自初始化为 2 GiB。
7. 双服启用后，至少覆盖一轮 09:00、14:00、19:00 的自然时点，并取得两服各一次相同来源无变化证据。记录计划/实际开始时间、生产与归档版本、耗时、结果和归档容量；调度延迟不冒充程序阻塞，也不忽略归档加入后的资源排队。
8. 完成手动补存、清理、关闭归档的演练，再按需要恢复自动保存。此步骤只处理获批的测试档案，记录实际释放量和已清理不回补结果。

这不是新增后台监测或自动化；发布验收时人工读取已有结果即可。若自然调度/素材尚未满足条件，验收保持未完成，不用手动运行冒充定时成功。

### 14.3 生产影响的判定与处置

出现以下任一情况即阻止启用或关闭归档：

- 原三时点/区服/模式或生产锁改变，生产等待归档，归档结果改写生产回执，或归档取得生产写路径。
- 无变化生产因归档待办持续进入完整恢复，或仅修改归档实现却持续改变生产指纹。
- 归档占据已不足的账户执行名额/资源，能观察到生产因归档竞争排队或延迟；官方访问限流出现与双任务并发相关的退化。
- 共同容量统计不能证明不超 2 GiB，或清理可能删除生产对象、错删新引用、已清理对象自动复活。

对不可复现的时延变化保留完整数据并继续分析，不能直接归因于 GitHub，也不能凭一次快运行宣称无影响。先撤去归档负载，再比较生产原路径；不以降低生产校验换取耗时好看。

## 15. 回退与保留

1. 优先将两个归档执行开关设为 false，停止后续归档 job；保留原生产开关、三次 cron 和正在执行的生产任务。
2. 归档执行器支持只停止自身：在文件边界停止新任务，处理或记录未完成上传/清理和预留。不要通过取消整个工作流来关闭归档。
3. 若在途归档导致紧急风险，可单独停止其进程/job，并在再次运行时先恢复账本/清理状态；未知删除结果不得计空闲，未知上传仍计占用。手动停止不应重置观察基线或删除档案。
4. 工作台可保留只读档案和不可用原因，后台关闭后如实显示无下一执行时点；已到期内容仍不能下载。必要时仅隐藏档案模块，不阻止原管理功能。
5. 默认不回退整个生产工作流。若必须回退该文件，说明它可能再次改变生产指纹并按原门禁接受完整路径；不能覆盖生产 checkpoint 或公开内容指针来“恢复”归档。
6. 清理已实际删除的原件没有自动回滚；窗口内只能按原身份与明确授权尝试重新取得。保留有界墓碑/诊断，不创建额外全量备份突破 2 GiB。
7. 若归档存储协议已写入新版本，旧程序未必能安全写；先关闭写入、验证只读兼容与账本，再处理版本回退，不能自动重建空账本。

完成标准：关闭归档后的下一个自然时点，原生产仍按预期执行；没有归档状态写入生产结果，未完成清理/预留有明确状态。
