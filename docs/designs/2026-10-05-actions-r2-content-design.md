# Actions 与 R2 内容生产和发布设计

状态：经站点所有者确认的目标设计。实施时每个切换关口仍以实际验证结果为准。

## 目标与边界

- Global 与 JP 均由 GitHub 托管的 Actions runner 定时探测、生产和发布内容。网站代码、查询服务、机器人及社区数据仍由现有部署提供。
- 公开 JSON、媒体和 Live2D 以现有 `/content/` URL 协议交付，客户端继续核对指针、清单和文件摘要。现有网页入口不迁到 Cloudflare。
- 两服独立追新、独立发布、独立回退。上游拒绝、客户端升级或解码映射未知、磁盘不足、校验失败、R2 上传失败时维持上次成功的内容指针。
- 不把 APK、原始抓取、解密材料、客户端凭据、私有配置和中间产物放进公开内容桶、Git 仓库或 Actions artifact。
- JP 的“无人值守”含已验证客户端版本内的自动探测、下载、构建和晋级。遇到新客户端版本或未知解码结构时必须停止并报告；自动接受未知凭据或映射不属于目标。Global 现有解码入口同样执行这一门禁。

## 现状与阻碍

`tools/global_update.py` 已有 Global 完整更新入口，但 `state.json`、同步状态和候选回执含本机绝对路径；现有发布器将本地 release 封存与本地 `current.json` 切换合在一起。服务器任务一次真实运行约 77 分钟。`tools/jp_remote_sync.py` 只有探测、验证已知采集及有界下载，`tools/jp_phone_inputs.py` 依赖固定版本和手机采集目录。标准托管 Linux runner 的磁盘容量为 14 GB，必须在真实数据上证明工作集能装下，不能把通过离线测试等同于生产可用。

## 方案选择

1. **推荐：无状态任务与分阶段检查点。** Actions 每次从私有 R2 恢复经摘要验证的必要输入，按区服生成候选，封存公开快照，上传、复核后晋级；阶段回执与上次成功输入由私有 R2 保存。工作量较大，但避免依赖 runner 本地路径和 GitHub artifact 的保留期。
2. 整个服务器工作目录在一个 job 中恢复并运行现有命令。改动较小，但绝对路径、硬链接、磁盘峰值和失败重跑使其不能作为长期结构。
3. 每个资源模块拆为单独 job。可以缩小单 job 工作集，但跨 job 数据交换、协调和费用复杂；只在实际容量测试证明方案 1 不足时采用。

## 存储与身份

使用站点所有者已创建的两个独立 R2 bucket：

- **`otonote-production-state` 私有生产桶**：已验证客户端包与配置身份、原始输入、可重用下载对象、阶段回执、最后成功输入引用和失败诊断。对象按区服、来源版本和 SHA-256 命名；任何可变 `latest` 状态只指向不可变对象。历史数据删除通过独立审计，不由发布 job 自动完成。
- **`otonote-public-content` 内容桶**：只含允许公开的 `/content/releases/<24hex>/...` 文件与两服内容指针。私有 `.receipt.json`、APK、原始 RPC、缓存和解密内容不得上传。Bucket 不直接公开；只读 Worker 绑定它，仅允许明确的指针及 release 路径，支持 GET/HEAD，拒绝列目录与隐藏文件。

生产状态清单保存固定工作根目录、路径白名单、输入对象摘要与区服。现阶段沿用更新器的绝对路径回执，因此每次 runner 必须在同一绝对路径恢复工作目录；恢复必须重验摘要，不能信任对象名或历史 `passed` 字段。后续才可将所有旧回执迁为相对路径。

## 每服生产流

1. `schedule` 与人工重试触发对应区服任务。生产只从受保护默认分支读取代码；未受信任的 PR 不拿生产凭据。区服并发组不取消运行中的生产。定时事件可能延迟或丢弃，因此单独检查最后成功时间并报警。
2. 只读探测官方版本及包身份。与上次成功的源版本、客户端身份和生产代码指纹相同且没有强制重建时，记录 `unchanged`，不重复编译。
3. 从私有 R2 恢复摘要固定的基线和中间结果。Global 使用现有官方包发现、签名校验、资源获取与解码门禁。JP 先以已授权的客户端内置凭据只读探测，再从官方 CDN 获取版本化目录、Master 与必需资源；采集/包输入、签名及版本绑定必须可验证。发现客户端推荐版本变化或解码配置不匹配时停止，不能把旧采集当成最新。
4. 完成输入预检、两语言投影、候选验证和快照封存。私有输入和公开快照分离，失败候选不晋级。
5. 仅上传封存清单允许的公开文件到不可变 R2 key；每个文件的大小和 SHA-256 与本地回执一致。重试遇到已存在 key 时比对内容，绝不覆盖不一致内容。上传全部成功后重新读取清单与关键对象，核对引用完整性。
6. 写不可变晋级记录，使用旧 `current.json` 的 ETag 条件切换新区服指针。冲突时拒绝覆盖并重新检查。回退也使用条件写入与晋级记录。旧版和跨服引用继续保留。

## 站点读取与预渲染

现有网站域名已在 Cloudflare 开启代理。把该主机名的 `/content/*` 配为只读 Worker Route；其他路径仍到现有服务器。指针 `no-store`；不可变 release 可长期缓存。网关用 R2 Worker binding 读取，避免通过公开桶域名暴露非预期对象；不需要独立资源域名。浏览器的 URL 和摘要校验协议保持兼容。旧 Nginx 内容别名在切换期保留，供撤回 Worker Route 后回退。

现有预渲染器仍在服务器运行。新增只读物化步骤，按指针拉取本服及跨服的清单、所需 JSON 与少量加载图，并核对摘要；生成代码/内容配对 HTML 后才切换预渲染指针。内容指针先行而预渲染滞后期间，现有客户端回退路径继续工作。服务器上的旧内容保留至切换验收，历史清理遵循 `docs/OPERATIONS.md` 的引用检查。

私有管理页把生产归属明确标为 GitHub Actions，并链接到本仓库的内容工作流；服务器不持有 GitHub 写入凭据。管理节点仅从本机经 R2 物化校验的两服指针、物化回执和 HTML 渲染记录导出交付状态，分别标识“本机内容已物化”和“HTML 已渲染”；该状态不宣称远端 R2 当前指针或最新 Actions 任务成功。已迁移的节点使用显式配置标记与新状态模式，拒绝把旧本机更新器的历史运行记录显示为当前生产，其他资源节点保留原有状态合同。导出失败时显示不可用，不能沿用上一次成功结论。

## 凭据与部署责任

站点所有者负责创建两个 R2 bucket、发放仅针对所需 bucket 的 R2 API 凭据、配置 GitHub 受保护环境 Secrets、部署现有主机名的只读 Worker Route，以及最终的生产路由切换。仓库只提供配置示例、程序和部署说明，不保存真实值。GitHub 环境限制默认分支；PR 验证 job 不接触 R2 写凭据、游戏客户端凭据和解密材料。

## 验收与回退

- 合成 R2 协议测试覆盖不可变对象冲突、部分上传、清单缺项、条件指针冲突、失败不切换和回退；浏览器与预渲染仍按原 URL 验证摘要。
- 两服分别在 GitHub 托管 runner 上完成真实只读探测、容量测量和影子生产；14 GB 标准 runner 不够时改用更大托管 runner 或分阶段处理，不能降低原有空间门槛。
- 影子发布的所有资源读回正确，且网站主路由、跨服查询、媒体、预渲染与动态服务通过真实浏览器和 HTTP 验收后，才切换 `/content/*`。
- 切换期保留原 Nginx 配置、原内容库和旧指针；R2 发布故障仅报警并保留旧内容。跨服指针、旧 HTML 与已打开页面的引用未过保留期前不自动删除对象。

## 外部依赖与未满足时的状态

两个 bucket 和 Worker 测试地址已创建；R2 写入凭据、私有状态首次导入、真实托管 runner 和线上 Route 尚未验收，不能声称 R2 实际上传、线上切换或无人值守生产验收完成。JP 受信任 1.0.4 包已在本机验证，但当前官方只读版本探测返回 HTTP 403；任务应明确 `blocked`，而不是发布旧采集。
