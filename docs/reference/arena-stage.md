# 激奏舞台信息查询与配队入口设计

本文是激奏舞台信息查询、配队入口与 UI 的详细设计，同时保留已确认规则和既有配队研究。当前源码已实现信息页、配队承接页及不可变快照更新检查；真实资料核验与交付关口集中在[待办](../BACKLOG.md)。通用计分机制见[演出情景与激奏机制](performance-scenarios.md)，搜索与证书边界见[计算搜索](calculation-search.md)。

规则依据为 Global 1.1.0（build 86）的游戏内帮助、公共 Master、匹配版本客户端与热补丁，以及局部原生离线回放。抽歌后不能换队由用户确认。未开启真实对局；玩家排行榜使用独立的只读观察数据，规则结论不自动适用于其他区服、版本或服务端特殊结算。

阅读入口：[本次范围](#本次设计范围)、[信息页 UI](#信息页-ui)、[配队入口](#配队入口承接页)、[数据与更新](#信息数据契约与更新)、[开发与验收](#开发边界与验收拆分)。单独查游戏规则从[玩法与配置](#玩法与配置)开始；[既有配队研究](#既有配队研究后续复用边界)不属于本次实施范围。

## 本次设计范围

当前源码实现下述信息与入口范围，部署与真实资料验收另行执行。范围收敛为**信息查询、舞台配队入口和 UI**；后文保留的计算研究用于约束入口，不是本次算法实施清单。

| 本次包含 | 本次不展开 |
| --- | --- |
| 独立舞台信息页、导航入口、区服／赛季／乐队切换 | 固定队伍的多曲目标、搜索算法、候选生成和性能调优 |

| 段位门槛、基础 AP、奖励及参赛规则查询 | 真实胜率、完整 AP 预测、自动上分建议 |
| 配队入口承接页、条件摘要、跨页传参与失效提示 | 尚未接入计算器时提供伪可用的“开始计算” |
| 桌面／手机布局、加载／缺失／历史／过期状态，沿用共用邮箱认证查询本人排名 | 新建登录体系、持久化游戏会话或真实对局 |

首版满足三件事：用户能查清某乐队当前的舞台条件，能理解规则与基础积分，并保留同一上下文的配队承接能力；当前页面配队按钮禁用。信息查询不依赖个人卡库、计分规则是否可用或玩家登录。

### 页面组织选择

| 方案 | 取舍 |
| --- | --- |
| 独立信息页＋薄配队承接页（采用） | 信息可独立发布；承接页只负责舞台条件与能力状态，后续复用既有配队器，不新建计分引擎 |
| 全部放进现有配队器的一个模式 | 查询规则也要进入复杂工具；未接入算法时容易误落到普通配队，不适合本次范围 |
| 为舞台新建完整门户与独立计算器 | 页面、卡库和计算逻辑重复，当前需求不需要 |

## 页面、导航与链接

以下路由沿用站点现有区服／语言前缀，不改变已有工具链接。

| 页面／入口 | 路径与行为 |
| --- | --- |
| 激奏舞台信息页 | `/{region}/{locale}/arena/`；站点“活动”分组新增“激奏舞台”，排在活动总览之后 |
| 舞台配队承接页 | `/{region}/{locale}/tools/arena/`；使用现有工具页框架，显示当前条件、入口状态和返回信息页的链接 |
| 信息页主操作 | “舞台配队”按钮禁用，旁边说明计算尚未开放；兼容既有承接页直达链接，不提供可点击的页面配队入口 |
| 工具目录快捷入口 | “舞台配队”；无有效舞台选择时先进入承接页选择条件，不能假定某乐队 |
| 原有配队器 | 后续以明确的舞台能力接入承接页；本次不改变普通／激奏模式的行为 |
| 玩家排行榜 | 信息页内展示，跟随账号区服、赛季和乐队选择；查询独立只读观察接口，缺失、官方空响应、失败和过期分别提示，不从静态 Master 推断真实排名 |

`region` 是内容版本（现有 `global`／`jp`），`serverId` 是账号区服；两者不合并。现有 Global 的港澳台、韩服、EN 标识沿用 `game-servers.mjs`，语言不决定区服。Global 公共快照不能自动证明所有账号区服的开放时间相同；展示资料范围，未经确认的区服不启用当前舞台配队。

信息页支持 `server`、`season`、`band`、`regulation`、`view`、`music` 查询参数：

- `season=current` 为默认，运行时解析；明确的赛季 ID 可查看已发布资料，未收录的历史显示“该赛季资料未收录”。
- `band` 指乐队 ID；通过 league 映射找到规则，不把 `leagueId` 和 `bandId` 当成同一字段。
- `regulation` 只用于指定已公布条件的详情；它不能覆盖数据中的属性或三段类型。失效／未知 ID 显示提示并提供“查看当前条件”，不悄悄选另一期。
- `music` 为官方配对趋势所查歌曲的 Master ID；仅用于查找已收录的官方快照，不表示已提交参赛歌曲，也不会启动单曲配队。切区服／赛季／乐队清除该选择；复制页面链接和切语言保留它。
- `view` 兼容旧的 `overview`／`ranks`／`rules` 链接；页面始终展示看板，`ranks` 打开段位与基础 AP 弹窗，`rules` 打开奖励与规则弹窗，不再切换独立页签。
- 用户主动切换选择时更新 URL，浏览器前进／后退恢复选择。定时刷新和倒计时不产生历史记录。
- “复制页面链接”固化当前选中的赛季、乐队和规则 ID；同 ID 数据修订后显示最新发布内容及资料时间，不承诺该链接保存旧版快照。
- URL 不包含个人卡库、账号令牌或完整队伍；本次入口也不在后台写入已有队伍草稿。

初次进入优先使用有效链接参数，其次使用同区服上次选择；都没有时展示当前赛季的第一个可用乐队，并清楚高亮，用户可以立即切换。无当前赛季时展示状态及已收录赛季列表，不把最近一季冒充当前赛季。

用户主动切换乐队或赛季时，清除不属于新选择的 regulation 详情，回到新选择的概览；外部链接本身含不相容参数时则提示错误。自动轮换只更新“跟随当前”的视图；用户正在查看指定历史／预告详情时保持该详情，提供“查看当前条件”，不擅自跳转。

## 信息页 UI

乐队选择条复用同一组按钮，位于站点页头下方吸顶；显示乐队标识、属性图标与三段类型简写。手机可横滑，切换后保留横向位置并让当前乐队可见，不复制第二组选择器。主体滚动时仍可直接切团。

信息页是一张单页舞台看板，不再将概览、段位积分和奖励规则作为三个并列页签。用户首先确认乐队和当前三段条件，配队按钮保持禁用并说明状态；官方配对趋势紧邻当前条件，段位与基础 AP、奖励和长篇规则默认收起。

```text
激奏舞台                                      [刷新资料] [复制链接]
Season · 每日配置检查说明                  [账号区服 ▾] [赛季 ▾]
[乐队 Logo · 属性 · C/L/J] [乐队 …] [乐队 …] [乐队 …] [乐队 …]
┌ 当前舞台 ───────────────────────────────┬ 官方配对趋势 ─────────┐
│ 乐队 Logo / 名称                  当前   │ [查询歌曲 ▾]           │
│ 属性图标 / ALL 或五色属性 · LUCK ×3     │ [队长] [成员] [留影]   │
│ 不同类型时按顺序：COMBO › LUCK › JUST   │ 卡面 × 3（可查看全部） │
│ 有效时间（北京时间）     [时间详情 ▸]   │ 采集时间 / 趋势说明     │
│ 编成限制 / 抽歌后锁队        [舞台配队 ↗]│                        │
└───────────────────────────────────────┴────────────────────────┘
玩家排行榜：名次 / 玩家 / 按积分门槛换算的段位 / 榜单积分
已收录条件安排                         [段位与基础 AP ▸]
[奖励与规则 ▸]
[资料来源与时间说明 ▸]
```

视觉重点是乐队 Logo、属性图标与紧凑的条件行；三段相同合并为 `LUCK ×3`，不同时按真实顺序显示 `COMBO › LUCK › JUST`，使用既有任务语义色，不重复放大字母和完整类型。完整段落顺序保留在可访问名称中，点击可查看类型解释。当前舞台与配队入口合为同一块区域，以虚线分隔条件与操作，不再为每一段创建等高小卡。页面采用现有主题、字体和色彩变量，不引入远程字体。仅乐队栏可局部横向滚动，页面不能横向溢出。

| 信息 | 内容与交互 |
| --- | --- |
| 顶部上下文 | 区服、赛季与乐队切换；各乐队独立解析当前所选赛季，不沿用正在查看的历史行。没有真实覆盖信息的账号区服明确提示 |
| 当前舞台 | 乐队、属性、三个实际任务类型、当前／历史／预告状态及有效时间。类型短标保留完整可访问名称与点击解释，不只靠颜色表达 |
| 歌曲相关条件 | 协议值 0 仍原样保存在官方条件与身份中；展示时按当前查询歌曲解析对应属性／任务。不把 0 做成第四种任务类型，不在用户界面写“沿用原曲”。需要歌曲且链接未指定时，优先采用该乐队默认趋势查询歌曲；没有可用趋势快照时采用目录中第一首可查询歌曲。明确展示可切换的歌曲选择并写入 URL；这不是提交参赛歌曲，也不推断用户拥有该曲。指定歌曲不存在或类型缺失时提示选择／资料缺失，不填造 C／L／J |
| 配队操作 | 与当前条件放在一起，明确成员范围、留影范围和抽歌后锁队。承接页在计算未接通时继续明确展示状态，不启动普通配队 |
| 段位与积分 | 上方入口打开共用弹窗，按赛前段位与人数查询基础 AP，不跟随主乐队筛选变化。相同门槛合并展示，差异和缺失分团明确展示；不显示虚构的个人段位 |
| 条件安排 | 只显示已收录的官方配置。相邻同值保留各自有效期，历史和预告明确标识；未知后续不生成倒计时或循环 |
| 奖励与规则 | 上方入口打开共用弹窗，保留领取说明、已核验奖励与规则；晋段奖励保留乐队归属。奖励关联未确认时显示缺失，不影响当前条件查询 |
| 来源与时间 | 观察时间、账号区服覆盖、赛季时间、区服源时间语义放在可展开区域。页面统一显示北京时间，绝对时间和官方源时区分别保留；有效区间不含结束时刻，不把页面打开时间当作官方更新时间 |

桌面与手机均按当前条件、紧凑配队入口、独立趋势卡片、玩家榜排列，不将趋势列表拼接在条件右侧。条件安排、段位／基础 AP、奖励规则三个入口置于上方，均使用原生弹窗。安排跟随当前赛季与乐队；基础 AP 和通用规则独立于主乐队选择。趋势默认只预览一组，完整列表进入独立滚动弹窗，切换类型不拉长当前条件。沿用工具设计系统的 13px 正文、12px 辅助字、8px 圆角、桌面 34px 控件与手机至少 44px 触控区域，乐队选择保留选中态和键盘焦点。弹窗默认关闭，来源说明默认折叠，异常状态及当前有效期保持可见。320／390／768／1280 宽度和 200% 等效缩放均需验收。

### 玩家排行榜

信息页在当前舞台与官方趋势区域下展示紧凑榜单，不占用主视觉；名次、玩家名与榜单积分按官方返回值展示，积分不标为 AP。分数旁的段位标记是按快照积分与同版门槛换算，非官方响应直接返回的玩家实时段位。无需网站用户登录，不读取个人卡库或个人排名；只投影榜单响应中的公开编成。匿名访问没有访问者的游戏身份，因此不提供“我的排名”，采集账号不能代替访问者。昵称按文本转义，官方同分并列及名次间隔保留，不用列表序号重排名。

- 查询 `GET /api/v1/arena-rankings?server=<serverId>&season=<seasonId>&band=<bandId>&limit=10`。三个身份均明确给定，读取 `observations/<serverId>/arena/season-<seasonId>/band-<bandId>.json`；区服、赛季、乐队不能相互回退。源文件不与活动榜 `current.json` 共用。
- 切换任一身份立即清空旧条目并取消前一个请求。响应再次核对三项身份，迟到响应不能覆盖新选择；切换歌曲、条件时段和基础 AP 查询不改动榜单身份。
- 接口 `unavailable` 表示本选择未采集；`empty` 仅用于成功读取且官方确实返回空区间；`stale` 保留原采集时间并明确是已过期记录。404、网络／解析／校验失败显示读取失败，不变成“暂无玩家”。过期的空快照也不能声明当前没有玩家。
- 首次显示 10 条，滑近末尾自动加载下一页，同一时刻只发起一次请求；保留手动按钮供键盘与不支持观察器的浏览器使用。自动追加保留已有队伍展开状态和阅读位置；失败停止自动请求，必须明确重试。切换身份、游标变化或离开页面中止旧观察器与请求。采集器默认读取每个乐队前 1000 名区间，每次游戏请求最多 100 名，单次认证内顺序分页，页面说明覆盖范围，不把 `maxRank` 当成本站完整条目数，也不推断全服人数。
- 翻页游标绑定区服、赛季、乐队及源文件 SHA-256。快照更新或游标跨范围返回 409，页面清空分页状态并提示重新载入，不合并两个时间点的榜单。加载更多失败仅保留同一次已加载记录，可重试。
- 段位换算要求观察记录的 `sourceReleaseId` 与当前配置版本相同，且账号区服覆盖、赛季、乐队和采集时刻均匹配。只使用采集时已开放且门槛清楚的该乐队段位，采用包含起点的积分区间；跨区服、跨版本、采集时刻不在赛季内、缺失或冲突门槛显示“段位待核验”，不补造。过期榜单仍保留原分数及当时换算标记，不声称玩家当前仍处于该段位。
- 观察数据独立于不可变内容投影发布：静态 `capabilities.rankings` 不保证实时榜单可用；真实状态以所选观察接口为准。响应带采集时间和到期时间，过期边界会更新提示。保存观察接口只读文件，不在 Query 服务中触发游戏登录或采集；独立按需捕获接口见下文。

采集程序 `tools.collect_arena_rankings` 沿用现有小号 SDK 配置、只读 credentials 挂载与共用 `capture.lock`。公开内容 pointer、manifest、舞台投影逐级验证 SHA-256，只有明确覆盖该账号区服、已开始的所选赛季和乐队才允许认证；也支持显式本地受审投影及必填摘要。服务发现和版本协商发生在认证前。不从语言、可选乐队或 HMT 配置推断其他账号区服开放。

已核对 Global 1.1.0 的 `app.arena.ArenaService/ArenaRanking` 请求字段：1 赛季、2 乐队、3 开始名次、4 结束名次；响应字段 1 排名列表、2 最大名次；条目字段 1 公开资料、2 队伍、3 名次、4 积分。只白名单保留公开玩家 ID／名、名次、积分及公开编成。编成复用现有 `DeckDetail` 白名单：综合力、五个位置、演出顺序、成员／留影 Master ID 与公开养成字段；额外资料、认证信息和原始响应不进入公开观察文件。榜单行提供五张成员缩略预览，点击“查看队伍”展开详情，保留成员与留影位置关系、缺项和区服卡牌详情链接；说明这是排行榜附带的玩家队伍，不一定是获得当前积分时使用的队伍。原子发布前先校验整轮返回，解析失败保留旧文件和旧采集时间。认证、限流和已有采集暂停不自动重试或解除；不会请求个人周边排名、奖励、匹配、保存队伍或报告已读。

运行参数与现有观察服务的交付边界见[玩家榜采集运行约定](../runbooks/rankings.md#舞台玩家排行榜)。真实区服响应与线上交付验收继续记录在待办，不以接口定义代替开放验收。

段位徽章保留小尺寸官方游戏图标（桌面 22×24、手机 18×20）、段位文字与区分颜色。`rankIcons` 是受审输入的可选数组，包含 `tier`、Master 根目录下的相对 `path`、原始 WebP 的 `sha256`；图标须从对应版本中核对层级映射。投影只发布 `tier`、小体积 WebP data URI 和摘要，每个不超过 64KiB，最多七个层级。路径逃逸、摘要不符或非法字段关闭图标投影，文字及其他舞台能力继续可用；不把私人路径或资源提取记录带入公开快照。

### 按需名次查询与低频更新

默认读取已保存的前 1000 名榜单。指定单个名次或起止范围时，读取 `/api/v1/arena-rankings-live`，参数为 `server`、`season`、`band`、`rank`、`end`、`limit` 和可选 `cursor`；结束名次留空时查询单个排名。允许超过第 1000 名，但每次范围最多 **100 名**，在浏览器、HTTP 参数与捕获器三个边界校验，拒绝倒置或超宽范围后不会登录。`rank` 与 `end` 随复制链接保留，切区服、赛季或乐队清除。未接通（404／501）明确提示并提供返回前 1000 名的按钮，不用保存榜单冒充范围查询结果，也不自动跳到下一范围遍历全榜。

当前港澳台 Global 1.1.0 已实测超过第 1000 名的区间、官方报告的榜尾及榜尾之外的空响应。单次 100 条成功，101 条及 200 条被拒绝；本站指定范围只发起一次官方榜单请求，不把本站批量采集的 T1000 当作官方总范围。`maxRank` 是本次官方返回的最大名次，会变化，不能硬编码成总人数或固定上限；它也不能证明“所有有分数玩家都会入榜”。

独立捕获进程 `tools.arena_live` 负责公开名次读取，Query 服务仍只读保存资料，不持有 SDK 或账号凭据。所有网站访问者共享同一区服、赛季、乐队与查询区间的 5 分钟缓存；并发相同查询合并。整站冷查询最多每分钟一次，只有实际访问且缓存失效时才读取官方，没有常驻全榜轮询。该预算只约束动态入口，活动／批量捕获继续使用各自计划与共享登录锁，交付时还需核对合计请求量。官方、SDK 和共享登录锁的暂停规则不因网页重试而解除。缓存最多 32 个范围，连接数有界；失败不更新旧结果时间。

页面每分钟检查一次本站公开接口；保存榜单已加载超过 100 条时暂缓静默替换，保留阅读位置，可手动刷新。切后台暂停；正在展开队伍、编辑名次或打开个人查询弹窗时暂缓自动刷新。静默检查失败保留原结果并提示。范围内按缓存游标分页，缓存更新或过期后返回 409，禁止跨时点拼接。429 返回重试间隔，页面不循环抢占查询预算。手动刷新同样遵守缓存和限速，不代表强制绕过官方读取间隔。

页面不提供段位范围筛选。官方 `ArenaRankingRequest` 没有段位、积分上下限参数；段位人数改由独立后台任务低频探测，不能将当前加载条目的分布当成全榜分布。

### 大段位人数与榜单规模

人数区跟随区服、赛季、乐队，只读取 `/api/v1/arena-population` 的保存汇总，不在访问、刷新、切换乐队时登录或启动探测。没有汇总时显示各大段位名称、官方图标及“—”；可展示所选榜单快照的最大名次和原时间，明确标签为“榜单最大名次”，不冒充全服独立人数。

Global 1.1.0 客户端已核对：`ArenaRanking` 提供所选榜的 `maxRank`；`ArenaRewards` 请求字段 1 为赛季，响应字段 3 的各乐队排名项包含乐队、本人名次和 `MaxRank`。后者是否支持进行中的赛季仍未实测，不据此启用新读取方法。当前客户端舞台接口未发现各大段位人数汇总字段，不把协议搜索等同于服务端穷尽证明。

`tools.collect_arena_rankings --population` 为独立的服务器探测模式，复用采集配置、只读凭据、版本协商、既有角色认证、共享 `capture.lock` 和暂停状态；不采集全榜、不写玩家操作、不读取本人排名或领奖。此模式只统计大段位，按同版积分门槛二分查找边界，每个榜单请求仅查一个名次，结果只保存总量估算、大段位计数及时间／版本信息，丢弃公开资料、队伍和采样玩家。最大名次用于榜内规模估算，不含未上榜者；同一玩家可在多个乐队上榜，不能相加作为全服独立人数。

受审输入的 `masterVersion` 必须与认证前的官方 Master 版本匹配；`completeRankBands` 由构建器比较该乐队全部源段位 ID 与发布 ID 得出，部分发布的门槛不能用于人口探测。只对已核验账号区服、正在进行的赛季、明确开放的完整大段位门槛运行。每团最多 96 次单条读取、相邻请求至少间隔 1 秒、开始后 180 秒停止发起新请求；同一账号区服每次尝试后冷却 6 小时，失败及人工重启不绕过冷却。没有浏览器触发入口，也不自动安装计划任务。

每次采样核对最大名次、名次位置、已采样积分的降序关系，最后复核榜头、榜尾、榜尾之外和各段位边界，并再次核对公共 Master 版本、赛季结束时刻。发现榜尾变化、边界移动、顺序异常、超时、预算不足或门槛版本不符即停止，整轮通过前不替换旧汇总。官方未提供一致快照令牌，多个请求仍可能跨时点，因此成功结果始终标记“榜内人数估算”，展示探测起止时间；不能宣称为官方实时精确人数。

汇总与榜单文件分别保存；三项身份、Master 版本、内容版本、完整门槛及赛季时间均匹配时才显示段位数字。过期保留旧估算及时间，缺失、失败、版本不匹配均明确提示，不补零、不使用其他乐队或区服的数据。真实探测、常驻任务和正常内容交付仍见[待办](../BACKLOG.md)。

### 我的排名与段位

榜单标题旁“我的排名”打开独立弹窗，跟随当前账号区服、赛季与乐队。沿用[共用邮箱认证](account-reads.md)，`POST /api/growth-export/arena-rank/` 仅接受 `account`、`password`、`serverId`、`seasonId`、`bandId`；不允许玩家 ID、任意目标账号令牌或名次范围参数。每次提交由本次 SDK／游戏认证决定查询者身份，不使用采集小号或公开缓存回答“我的排名”。

Global 1.1.0 客户端已核对 `app.arena.ArenaService/ArenaMyRank`：请求字段 1 为赛季；响应字段 1 为总积分／名次，字段 2 为各乐队数据（1 乐队、2 积分、3 名次）。只调用一次本人接口，白名单输出所选乐队；总积分不冒充乐队积分，不遍历公开榜单、不读取卡库，不调用 `ArenaTop`、领奖、匹配或角色创建接口。实际账号响应仍须单独验收。

已返回记录但名次为 0 与未返回该乐队分别显示“未上榜”“未返回记录”，不能统一补成 0 名或新手。个人接口没有直接返回段位：认证前的公共 `Masterdata.Version` 字段 1 与受审投影的可选 `sourceMasterVersion` 一致，且账号区服、赛季、乐队、查询时刻及门槛均匹配时才换算“积分对应段位”；否则显示“待核验”。`sourceMasterVersion` 来自受审输入 `masterVersion`，未知时留空，不能从客户端版本号猜测 Master 一致。

个人查询复用 Host／Origin／nonce、no-store、并发与限流；nonce 不是玩家会话。没有定时个人查询、密码重发或跨请求登录。凭据提交后立即清空输入；个人结果只留当前弹窗内存，不进入观察文件、共享缓存、URL、浏览器存储或内容发布。关闭弹窗、切区服／赛季／乐队、离开页面或失败都会清空，迟到响应不能覆盖新选择；重新查询必须重新认证。界面提示登录可能使游戏会话失效。

源代码、部署示例和本地验证不代表动态服务或个人查询已经上线；同源代理、网关／捕获镜像、真实账号和正常内容交付仍须通过[运行约定](../runbooks/rankings.md)与待办。

### 官方配对趋势

信息页与承接页提供独立的“官方配对趋势”区域，按账号区服、所选赛季、乐队及歌曲精确查阅受审快照。官方 `ArenaService.DeckTrend` 请求包含歌曲、赛季和乐队；账号区服由采集环境明确绑定，不能从语言或公共内容版本推断。

- 信息页默认选择该乐队已收录且有条目的第一首查询歌曲，无条目时选择第一首已收录歌曲；明确展示歌曲选择并写入 URL。不是提交参赛歌曲。指定未知歌曲时不回退。
- 信息页默认预览队长，支持队长／成员／留影切换；桌面预览官方顺序前六张、手机前三张卡面。“查看完整趋势”打开原生对话框，支持内部滚动、类型切换、Escape 关闭与返回触发按钮焦点。切换查询范围会关闭旧对话框，切换歌曲后重新展示对应快照。统计与语义说明收起，承接页保留完整分组。
- 分别展示官方响应中的队长 `leaders`、成员 `members`、留影 `supports`；保留官方返回顺序，支持类型筛选及卡牌详情跳转。缺卡面保留名称，目录未收录的卡牌保留其 ID 和原位置。
- 三组条目不建立成员与留影的一一配对，不从数组位置推导配对关系。官方文案称为热门编队，但未说明入选规则；响应只有三组 ID，不提供使用率、统计周期或样本量。序号不是使用率，协议字段也不能证明最优队伍或胜率。
- 展示快照观察时间与显示时区；观察时间不冒充官方统计截止。快照位于所选条件时段之外时明确提示，不把赛季级歌曲趋势误称为当前 regulation 的实时趋势。
- 未选上下文时提示补齐选择；无快照、校验失败和真实空响应分别展示。没有快照时不放模拟卡牌、百分比或虚假使用人数。
- 浏览器只读同一内容快照，不直接请求游戏接口。`tools.collect_arena_trends` 使用既有采集账号、SDK 与共享登录锁，按同版公开目录的歌曲、赛季与乐队进行最多 200 个顺序查询；当前曲目来源只支持受审投影和目录及其必填 SHA-256。只读 `DeckTrend`，只保留三组卡牌 ID，经既有白名单投影进入内容候选。失败保留旧观察，认证／限流暂停不自动重试。
- 真实响应可以为空。当前港澳台五个乐队的目录查询已完成本地验证；其他区服、其他赛季及正常内容候选交付仍单独验收。曲目目录与舞台投影版本不一致、区服覆盖未核验时停止，不从歌名或卡牌属性推测趋势。

### 段位与积分查询

共用积分弹窗展示段位梯级，默认按大段位折叠，展开可见小段位名与对应门槛。只有各乐队的层级、门槛、名字与开放约束逐项一致时合并；差异单独列出，缺失资料不拿其他乐队填补。当前版本五个乐队的已核验门槛相同，段位与积分仍分别记录。段位名、门槛及开放状态从表读取；没有个人数据时不放“我的段位”进度条，也不标记玩家当前所在档。

弹窗上部是“基础 AP 查询”：选择**赛前大段位**和对局人数（2～5），展示各名次对应的基础 AP。初始可展示表中第一个大段位及 5 人局，控件明确可修改，不使用“你的对局”。正负数保留符号，颜色只是辅助。缺少该组合时显示“当前资料没有此积分配置”，不能补零。

结果旁固定说明“基础 AP，不含道具及服务端其他修正”。道具、跨段、赛季重置及特殊结算只展示已确认规则，不给最终积分预测。AP 与尚未确认的总积分分类分别处理，不因协议字段出现而增加总榜。

### 奖励与规则弹窗

按用户问题分为“如何参赛”“奖励如何领取”“段位与赛季如何结算”三个内容组，默认展开参赛条件与奖励摘要，详细表格折叠。

- 参赛摘要：成员来自所选乐队、留影不限、提交自己拥有的该乐队歌曲、匹配后抽歌、抽歌后不能换队。
- 每日奖励：明确是所有乐队合计最多 3 次；显示重置时间，不显示未经账号读取的已领／剩余次数。
- 首次晋段：列出已核验的乐队归属和奖励门槛，不随主乐队选择筛除其他乐队；不推断个人是否已领取。
- 赛季奖励：解释按所有乐队中该赛季最高达到段位结算；不要误标成当前乐队独占奖励。
- 奖励物品仅在关联表与物品资料可解析时显示名称、图标、数量；缺少图标保留文字，缺少内容显示资料暂缺，不捏造奖品。
- 断线、处罚、继承规则以已确认帮助为依据；未还原部分明确写“具体调整规则待确认”，不把静态字段值当完整公式。

帮助文案与配置值分离：玩法解释可以随代码维护，次数、有效时间、段位门槛、基础 AP 和奖励数量随数据发布。文本内容通过安全文本节点渲染，不直接执行原始 Master 富文本。

## 配队入口承接页

本次只实现入口和条件交接，不设计卡片推荐算法。承接页复用工具页布局，但在舞台计算能力未接通时，不挂载普通配队器、不触发搜索、不加载全卡库。

```text
舞台配队                          [返回激奏舞台]
所选区服 / 赛季 / 乐队             当前条件 · 有效至 …
属性 [名称]    第 1 段 [类型] / 第 2 段 [类型] / 第 3 段 [类型]
成员仅限所选乐队，留影不限；抽歌后不能换队。

舞台配队计算尚未开放。
当前条件已就绪，计算功能接入后将在这里使用。
[查看舞台规则] [复制条件摘要]
```

信息页上的“舞台配队”在首版可点击进入上述真实页面，并有“查看条件，计算暂未开放”的辅助文字；不使用假加载、空进度条或可点击却无反应的“开始计算”。之后算法能力就绪，再在相同路由挂载既有配队组件，替换状态区；不会另建一套卡库。

入口状态独立于信息查询：

| 状态 | 信息页／承接页行为 |
| --- | --- |
| 当前条件有效，计算未接通 | 可进入承接页；展示条件及“计算尚未开放”，提供规则与复制摘要 |
| 当前条件有效，后续已接通计算 | 同一路由可加载舞台配队功能；仍须满足计分数据兼容门槛，此行为不在本次实施范围 |
| 未选账号区服 | 信息仍可按内容版本查看；承接页要求选择账号区服，不自动访问或迁移其他区服卡库 |
| 历史／预告条件 | 可查看详情与复制；不提供当前参赛配队，提供明确的“查看当前条件”操作 |
| 条件缺失／冲突／不支持 | 解释原因，保留返回信息页与刷新操作；不回退普通或自由激奏 |
| 点击后条件已变化 | 展示最新条件和“舞台条件已更新”；保留新旧摘要（若旧摘要可用），用户明确使用当前条件后继续 |

交接仅携带区服、赛季、乐队、regulation ID 和当前上下文摘要。接收页从受验证的内容重新解析，链接内属性和三段类型不具有权威性。复制摘要为普通文本，包含所选条件、有效时间、资料时间及“抽歌后不能换队”，不包含账号资料。

如果从工具目录直接访问、缺少参数，承接页提供与信息页相同的区服／赛季／乐队选择器，解析完成后显示摘要。不提供任何默认“已匹配”或“已保存专用队伍”状态。返回信息页保留当前视图；跨页传参本身不保存或覆盖用户队伍。

## 信息数据契约与更新

### 数据生产与展示分离

采用现有内容发布链，新增经过白名单投影的 `projection/arena.json`，随同一内容 manifest 交付。浏览器通过已有 `artifact` 读取，不直接请求游戏接口、不接触解密密钥，也不把原始协议或私有证据发布到站点。未包含该文件的旧内容快照显示“舞台资料暂未提供”，不影响其他页面。

| 来源 | 投影内容与校验 |
| --- | --- |
| `MasterArenaSeason` | 赛季 ID、名称、开始／结束、统计截止，分别保留语义 |
| `MasterArenaLeague` | league ID、乐队 ID、名称、开放约束；显式建立 league → band 映射 |
| `MasterArenaLeagueRegulation` | league 引用、属性、三段类型、开始／结束；保留 0 回退与 99 ALL，不在信息层替换成某首歌的值 |
| `MasterArenaRank` | 乐队、段位层级、小段位、门槛、开放约束；未确认的重置字段不直接成为 UI 公式 |
| `MasterBattleLivePlace` | 赛前段位 × 人数 × 名次 → 基础 AP；缺项不补零，重复冲突拒绝该功能 |
| 每日／晋段／赛季奖励表、帮助与物品目录 | 已核验的显示字段及物品引用；未知关联只影响对应奖励区域 |

当前投影外层字段：`schemaVersion`、`region`、`sourceReleaseId`、`observedAt`、`sourceRevision`、`serverScopes`、`timeZone`、`timeSemanticsVersion`、`capabilities`、`seasons`、`leagues`、`regulations`、`ranks`、`basePoints`、`rewards`、`dailyReward`、`deckTrends`、`limitations`。以下语义必须保持：

- `sourceRevision` 绑定舞台相关源表和受审条件摘要；配置 ID 不变但内容变化时也更新。趋势观察与图标分别校验，不因趋势刷新或图标变化改变舞台条件身份；内容指针仍按整份不可变快照更新。
- `serverScopes` 明确此资料覆盖哪些账号区服，未确认不填成“全部”；跨语言仅换文案，不改变数值身份。
- 时间转换由数据生产侧按已核验区服时区与端点精度执行，输出绝对时间；客户端不靠 `new Date(无时区文本)` 猜测。规范化区间使用 `[validFrom, validUntil)`，源数据如何映射必须有边界用例。
- regulation 本身没有直接赛季字段时，以时间与所选赛季求交集，不补造外键。同一 league 同时命中多个相互冲突的配置时，当前条件为不可用，不取数组第一条。
- 能力分别声明 `conditions`、`ranks`、`basePoints`、`rewards`、`rankings`、`deckTrends`；信息局部缺失不导致整页失败。实际计算能力还受代码版本与计分数据门槛约束，不能被一个内容布尔值直接打开。
- 对外只显示已经进入正常发布范围的资料；本机解包得到的未来表项不因“存在”就自动公开。本轮不新增未来内容公开策略。

当前时区／端点语义若尚未完成核验，可展示原始时间的说明性文字，但不能提供精确倒计时或标成可用的当前参赛上下文。完成确认后再打开相应能力；该缺口不阻止静态玩法说明页。

### 当前生产输入与核验闸门

`tools/arena_content.py` 通过 `build_catalog` 生成 `arena.json`，随正常候选链封存，
发布器登记为 `projection/arena.json` 并校验区服与内容身份。旧候选没有该文件时仍可发布，
浏览器以可选 artifact 读取，显示缺失状态。没有核验输入的新候选生成能力关闭的空投影，
不会自动公开本机研究材料或全表未来安排。

私有内容输入计划的所选环境可提供 `arenaReview: {path, sha256}`。路径按现有输入根解析，
摘要固定核验 JSON 的字节；文件不得逃逸输入根。`compile_core` 一次读取后供两语言复用，
候选生成前后重新检查摘要与内容，不把核验文件、路径或原始表复制到公开投影。
核验文件保存在仓库外的受保护生产输入中，不随本次源码附带真实配置。

| 核验输入 | 当前契约 |
| --- | --- |
| 身份和资料范围 | `schemaVersion: 1`、`region`、`sourceReleaseId`；可选绝对时间 `observedAt`；`serverScopes` 只列已确认账号区服 |
| 源表白名单 | `tables` 按 Master 表名保存 `sha256` 与 `publishedIds`；摘要绑定完整源文件，只有明确列出的行进入投影。缺少表绑定时该表为空，不能据此推断功能已开放 |
| 时间 | 可选 `time: {timeZone, semanticsVersion}`。当前适配器仅支持经核验的 `inclusive-second-v1`：无时区源文本精确到秒，起点包含，`_endAt` 与 `_rankingCountEndAt` 包含末秒；转换为 IANA 区服时区的绝对 `[start, end + 1 秒)`。歧义／不存在的本地时刻拒绝对应时间数据，未知语义不套用此适配器 |
| 活动边界 | `MasterEvent` 同样绑定源表摘要及 `publishedIds`；可选 `activityTime: {timeZone, semanticsVersion}` 独立核验活动时间，当前支持 `inclusive-second-v1`。只投影 `activityPeriods: [{id, validFrom, validUntil}]` 绝对区间，供同步检查使用，不从活动加成推算舞台属性；缺少核验时不生成边界。旧投影没有此字段仍兼容 |
| 奖励关联 | 可选 `rewardGroups`：`kind` 为 `daily`／`promotion`／`season`，指定受审 `rowIds` 与显示 `label`；晋段组还指定已核验的 `bandId`／`rankId`。`resourceItems` 显式建立 `资源类型:资源ID` → `MasterItem` ID 关系，不假定所有资源共享道具命名空间；数量仍读源表 |
| 每日配置 | 可选 `dailyReward` 提供已确认的 `limit` 与 `resetTime`；当前支持 `04:00`。所有乐队合计展示，不生成个人领取次数 |

私有核验输入可选 `deckTrends` 数组，由 `tools/arena_trends.py` 投影。每项显式提供
`source: "ArenaService.DeckTrend"`、`serverId`、`seasonId`、`bandId`、整数 `musicId`、
带时区的 `observedAt`，以及已核验的 `response`。规范化响应明确包含三个数组：
`leaders`／`members` 的条目提供整数 `memberCardId`，`supports` 的条目提供整数
`supportCardId`。这是受审快照的输入契约，不是未经验证的实时协议适配器。

对外仅投影查询范围、观察时间、三组 ID 和内容摘要；认证信息、个人编成、原始响应及
未知字段不复制到公开产物。不补造使用率或数量。同一查询保留最新的完整观察，
同一观察时间内容冲突则关闭趋势能力；错误不阻断舞台条件、段位和基础 AP。
发布器进一步校验字段白名单、摘要及区服／赛季／乐队引用。旧投影缺少趋势字段时仍兼容。

时间未核验时只展示赛季原始时间说明，不按未经确认的绝对时间把 regulation 归入赛季、
不标记当前可参赛条件。账号区服覆盖或乐队开放约束未确认时资料仍可查阅，承接页明确提示限制；未提供开放字段不等于没有开放限制。
奖励关联未确认只影响对应奖励区域；段位和基础 AP 分别保留自己的能力状态。
属性与三段类型仅来自受验证投影，URL 中的同名数值不会覆盖它们。

当前实现不读取个人卡库、不写用户队伍、不加载计算规则或启动搜索 worker。
页面隐藏时停止定时器，恢复时重解析；只检查内容指针，不热替换已固定的内容快照。
语言切换保留同一内容版本内的选择，账号区服选择复用站点的分服偏好键。

### 页面状态与新鲜度

信息状态与入口状态分开。页面固定在一份不可变内容快照，沿用 `runtime/content.mjs` 的规则，不热混合新舞台配置与旧目录。

| 情况 | 页面表现 | 可用操作 |
| --- | --- | --- |
| 首次加载 | 与真实布局等高的条件、安排占位；不出现假 ALL 或假任务 | 导航可用，入口等待解析 |
| 当前快照有唯一有效配置 | 显示条件、绝对有效时间和资料更新时间 | 查看说明弹窗、安排、复制、进入承接页 |
| 已收录下一期且到达时间边界 | 用同一快照重新解析，更新状态与条件；相邻同值也更新所属时段 | 提示“舞台条件已更新”，不强迫页面滚回顶部 |
| 边界后没有新配置 | 旧条件保留为“上一期”；当前区显示“新条件尚未收录” | 刷新资料、查看规则；不继续按旧条件交接 |
| 已有数据但刷新失败／离线 | 显示“当前展示已保存资料，未能检查更新”及资料时间 | 允许查阅、复制；不宣称已确认最新，不进入可计算状态 |
| 内容版本或摘要校验失败 | 显示明确错误及重试 | 不使用未验证返回，不回退其他区服 |
| 段位／奖励局部缺失 | 对应弹窗内显示缺失原因，当前条件区仍可用 | 其他功能继续使用 |
| 无赛季或未开放 | 显示“当前没有已公布的舞台赛季”，可查已收录资料 | 不以空表暗示接口失败，不伪造倒计时 |

“刷新资料”检查当前内容指针；指针未变则更新本次检查状态，指针变化则显示“有新资料，重新载入”，重载整页后采用新快照。本次承接页没有可丢失的队伍编辑，能保留 URL 选择并重载；后续加入队伍编辑时再复用草稿保护。

仅在页面可见时每 5 分钟检查一次指针，手动刷新、重新聚焦和配置边界可额外触发；同一时刻合并重复请求，后台不轮询。5 分钟是前端检查频率，不承诺官方热更新会在 5 分钟内被收录。内容生产以北京时间 03:00 替换原 09:00 固定检查，保留 14:00、19:00；已核验活动时间经正常配置变更登记为原生定点任务，到点触发对应区服的正常同步，不使用 Actions 五分钟轮询，详见[内容管线](../runbooks/content-pipeline.md)。页面也在北京时间 03:00 和受审活动边界额外检查内容指针。已发布的未来时段可以在本地边界自动切换，同值新一期仍更新身份；不按 C／L／J 循环生成条件。只有当前有效区间结束且缺少后续配置时才显示缺失，不因日期变化否定仍在有效期内的官方配置。

当前时间判断使用可注入时钟以便测试；默认设备时间，界面显示区服时区，不宣称已校准服务器时间。检测到设备时钟明显跳变时重新解析并提示检查时间。发起条件刷新与跨页承接都带请求代次，切乐队／赛季后的迟到响应不得覆盖新选择。

| 提交歌曲 | 从所选乐队已拥有的歌曲中提交 | 区分本人可提交歌曲与用于评估对手可能提交的曲池，不以本人拥有情况替代整个评估范围 |
| 抽歌与锁队 | 实际歌曲从有效玩家提交项决定，抽歌后无法换队 | 匹配前推荐固定队伍；指定歌曲估分与多曲适应性比较分别展示 |
| 属性与任务 | 舞台属性及三段激奏类型覆盖原曲配置 | 同时传到综合力、歌曲属性技能目标、激奏效果筛选和段落奖励；不能只改界面标签 |
| 轮换 | 帮助规定属性随活动切换、激奏类型每天 4:00 切换；相邻区间可能相同 | 按区服时间、赛季及 `MasterArenaLeagueRegulation` 的有效区间读取，不能推算固定循环 |
| 人数与积分 | 对局 2～5 人，基础 AP 取决于赛前大段位、人数和名次 | 局内得分、三段任务表现、对局名次、段位 AP 分开建模 |
| 每日奖励 | 所有乐队合计每日最多 3 次，4:00 重置 | 不显示为每乐队各 3 次 |
| 晋段与赛季奖励 | 首次晋段奖励按乐队；赛季奖励取所有乐队中该赛季达到的最高段位，下赛季发放 | 当前段位与赛季最高段位分别展示 |
| 赛季继承 | 白银 1 及以下 AP 原样继承，其余按规则降低 | 高段位重置公式仍待核验，不从字段名推导 |
| 中断 | 帮助说明中断／断线按末名处理；达到每日次数限制后，下次 4:00 解除匹配限制 | 服务端同分、零分、断线及特殊修正仍须独立对账 |

客户端抽歌按有效提交玩家的随机连接令牌选择提交项，没有先按歌曲去重。正常独立随机、全部提交有效且忽略令牌碰撞时，可推导每位玩家的提交近似等权；一首歌被多位玩家提交时，应累加其权重。这是代码推导，不是实测频率。对手提交分布未知，个人常用歌单和效率歌单都只能表示评估范围。

### 属性和三段类型如何覆盖

`ArenaLiveMusicData` 包装原 `MasterLiveMusic` 与舞台 regulation，按字段独立回退：

```text
有效属性 = regulation.musicType != 0 ? regulation.musicType : 原曲.musicType
有效任务[i] = regulation.mission[i] != 0 ? regulation.mission[i] : 原曲.mission[i]
```

`0` 表示回退；属性 `99` 是明确的 ALL，不能当成回退。三段分别处理，例如原曲为 COMBO／LUCK／JUST，覆盖为 JUST／0／COMBO，则实际为 JUST／LUCK／COMBO。有效属性同时用于 `MusicType`、`ParamMusicType`、`SkillTargetMusicType`。

歌曲 ID、谱面、音频、歌曲标签等仍来自原曲。覆盖歌曲属性不会修改卡片属性或乐队、留影配对关系，也不会把歌曲标签改成舞台属性。综合力仍分别处理歌曲属性匹配、歌曲标签匹配及卡片间的关系。

客户端加载谱面时把有效三段任务传入 `LiveMusicScore`。段落沿用原谱面 `FeverList` 的起止位置，按顺序赋予任务，最多取前三段；没有在该构造路径生成舞台专用时间轴。现有计算器要求恰好三个有效段落，缺失时应明确拒算，不能补造边界。

覆盖 getter 的 162 组、段落构造的 135 组原生离线检查通过。段落检查替代了集合、位置读取和音符区间读取，只证明边界对象及类型传递；不证明音符落在边界两侧时的完整调度、所有技能同帧顺序或网络确认时机均已验收。

### 计分与段位积分

新版音符计分核心的 4096 组离线向量与现有核心一致。已对照的音符参数、判定参数及窗口、连击加成、激奏排名奖励、LUCK 基础点数与抽选表，在基线覆盖字段上未变化。因此可以复用现有核心及三种任务模型，但不能据此宣布整个新版计分状态机已验证。

段落奖励仍按段落分数与排名奖励百分比计算。奖励表的组合分类取决于**覆盖后的完整三段类型**，必须重新选择；不能保留原曲的组合分类。段落任务计数决定排名比较，不能直接当作得分倍率。固定段落名次或假设对手时，输出都是相应情景下的估分，不能称为个人胜率。

## 既有配队研究：后续复用边界

以下计算研究不属于本次信息查询与入口开发范围，供后续配队设计复用。

推荐在现有激奏引擎前加入显式的舞台上下文解析：业务模式是舞台，计分路径仍为激奏。解析一次原曲与 regulation，生成不可变的有效歌曲视图，所有消费者使用同一视图；原始 Master 不改写。

| 方案 | 取舍 |

| 每次计算复制并覆盖 `LiveMusic` 行 | 离线探针可验证复用性，但单靠复制无法保证结果身份、缓存与页面同步；不作为正式契约 |
| 独立舞台计分引擎 | 已确认的核心和时间轴可复用，另建引擎会增加规则分叉，当前没有必要 |

| 现有能力 | 可复用部分 | 必须补齐的边界 |
| --- | --- | --- |
| 卡库、养成、综合力 | 原有数据和计算模型 | 新版完整 Master、成员乐队约束、有效歌曲属性 |
| 激奏模拟 | 原谱面、三种任务、排名奖励、发挥及随机样本 | 覆盖后任务筛选与组合分类；新版时序对照；舞台上下文贯通 |

### 固定队伍的多曲评估

评估单位是完整队伍 `T`：成员、留影、槽位配对、队长及养成假设固定。对曲池中的歌曲／难度 `s`，按同一舞台上下文和预先声明的发挥、技能顺序抽样、对手及随机假设得到 `score(T,s)`。

共享歌单的 `runPlaylistTeamBatch` 已能批量逐曲配队，但每首歌独立选择队伍，不能当作舞台固定队伍的联合目标。推荐舞台首版只做已保存候选队伍的比较，目标为声明权重下的平均分：

```text
value(T) = Σ weight(s) × score(T,s) / Σ weight(s)
选择 T* = argmax value(T)
```

现有 `evaluatePresetPool` 可复用矩阵生成思路；`selectPresetPortfolio(matrix, 1)` 的第一步已经等价于上述单队选择，`contributions.singleTeamScore` 也已给出每队加权均分。无需重写该数学逻辑，但入口、结果结构和多候选排名必须明确为固定队伍，不能沿用默认保留多队、逐曲选择最强队的组合展示。

反例：两首等权歌曲，A 得分为 120／60，B 为 100／100，C 为 60／120。固定队伍应选 B，均分 100；多队组合会在两首歌分别用 A、C，显示 120。这种组合收益在锁队舞台不能实现。现有函数的合成矩阵检查已复现该区别。

评估契约：

- 同一首歌的各候选使用相同玩家操作样本和随机种子策略，逐曲改变 `selectedSongId`／难度不改变队伍；技能顺序随机样本不能被误报为抽歌后允许重新编队。
- 曲池可选效率精选、用户常用或明确枚举的可能选曲。等权是默认比较假设；自定义权重需记录来源。相同歌曲／难度可以合并计算，但必须累加原提交项权重，不能先去重再等权。
- 每队输出逐曲分数、加权均分、覆盖曲目与缺失原因；段落计数和条件奖励单独显示。池内最低分、抽样最低分分别标明，不称为真实保底。
- 不同歌曲基准得分不同，平均绝对分会更重视高分曲。逐曲相对收益或最大遗憾可作为另一个明确目标，不能在同一排名中悄悄混用；首版不把它扩展为真实胜率或 AP 期望。
- 某队在某曲遇到不支持的技能、缺失谱面等情况时，标为不完整，不能删除该曲后重新归一化并与完整队伍直接排名。只有用户明确接受统一缩小曲池后，才对所有队伍重算。
- 未知对手提交分布、段落结果及服务端修正时，不展示真实抽歌期望、胜率或上分效率。默认 `[1,1,1]` 段落名次是情景输入，不是预测；三段同类任务尤其需要展示名次敏感性。
- 候选只来自已保存队伍时，只保证候选集合内比较，不给全卡库最优证书。后续搜索必须面向整个曲池评价固定队伍，不能拼接逐曲最优队伍得分。

### 轮换、结果身份与缓存失效

离线探针仅在私有作用域覆盖歌曲行，24 组属性／三段类型得到不同综合力和分数，却返回同一单曲 `inputHash`。原因是 `createGekisouSongCalculator` 的结果摘要未直接纳入有效属性和任务。这个探针证明新增覆盖层不能沿用该身份契约；它不是现有线上舞台缓存串用的报告。`evaluatePresetPool` 外层已对规则整体取摘要，也不能代替单曲结果、worker 和页面的统一上下文。

接入时区分三类身份，字段名称可以随实现调整，但不能漏掉语义：

| 身份 | 必须包含的语义 | 用途 |
| --- | --- | --- |
| 舞台上下文 | 区服、业务模式、赛季、乐队、regulation 身份及内容摘要、区服时区、赛季与规则相交后的有效期 | 判断结果是否属于当前舞台、是否过期 |
| 单曲计算身份 | 上下文、有效歌曲属性与三段类型、源数据版本及摘要、计分模型版本、谱面内容摘要、完整队伍／养成、发挥样本、随机与技能顺序策略、对手／名次、确认延迟及精度 | 结果可复算，区分会影响数值的所有输入 |
| 多曲评估身份 | 单曲身份集合、规范化曲池与累加权重、候选集合、比较目标及版本 | 防止曲池或权重变化继续显示旧排序 |

处理规则：

1. 在开始计算和接收结果时都检查上下文。请求携带上下文摘要及请求代次；切乐队、换曲池、跨轮换或收到新配置后，取消旧任务或丢弃其迟到结果，不能覆盖新页面。
2. 有效期按区服时间及 Master 契约解析；明确源字段端点精度，再统一为内部区间。检查赛季与规则交集，不能套本机时区。若缺失或冲突，显示条件不可用，不沿用上一期作为当前期。
3. 轮换定时、页面重新聚焦／恢复、数据刷新时重新解析。时间过期不依赖用户手动刷新；数据修订也不依赖日期或 ID 改变。同 ID 的属性、任务或有效期热更新必须触发重新判断。
4. 旧结果可保留用于历史查看，但标为过期，并显示对应条件；新结果完成前不冒充当前推荐。存档队伍保留，成绩及推荐需重算或重新验证。
5. 若相邻区间数值相同，仍更新当前上下文身份。可以另以完整数值依赖摘要复用计算内核结果，但必须重验证、重新封装当前有效期，不能直接把旧结果标为当前。
6. 原始谱面解析可按内容摘要复用；综合力、技能筛选、任务组合奖励及成品结果均受覆盖影响。不能原地修改规则对象后继续使用旧 calculator 闭包或其内部缓存。
7. 个人养成、规则表、技能支持范围、模型或谱面更新同样使相关结果失效。只变曲池权重时允许复用仍有效的单曲矩阵，但必须重新聚合并生成新的评估身份。

验收至少覆盖：只改属性、只改某一段类型、`0` 回退与 `99` ALL、相邻期同值、同 ID 热修、赛季交界、跨期迟到 worker、切乐队、后台恢复、离线缺配置、权重改变和养成更新。验收应同时检查分数、摘要、有效期与页面状态。
