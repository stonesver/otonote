# 激奏舞台规则、信息设计与配队

本文维护舞台规则、信息查询设计与配队行为。`/tools/arena/` 已实现读取已发布舞台配置的三段 JUST 配队，也可手动试配；独立信息页及其完整查询流程仍待实施，事项集中在[待办](../BACKLOG.md)。通用计分机制见[演出情景与激奏机制](performance-scenarios.md)，搜索与证书边界见[计算搜索](calculation-search.md)。

规则依据为 Global 1.1.0（build 86）的游戏内帮助、公共 Master、匹配版本客户端与热补丁，以及局部原生离线回放。抽歌后不能换队由用户确认。没有开启真实对局或读取真实舞台榜单；这些结论不自动适用于其他区服、版本或服务端特殊结算。

阅读入口：[当前 JUST 配队](#just-配队首版)、[信息查询设计范围](#本次设计范围)、[信息页 UI](#信息页-ui)、[配队入口](#配队入口承接页)、[数据与更新](#信息数据契约与更新)、[开发与验收](#开发边界与验收拆分)。单独查游戏规则从[玩法与配置](#玩法与配置)开始。

## JUST 配队首版

工具目录提供 `/{region}/{locale}/tools/arena/`。页面使用当前区服的个人养成，通过共享“卡库与队伍”入口导入已有个人养成 JSON；原文件和账号资料不随网页代码发布。用户选择舞台场次或手动乐队／属性、2–5 人、不超过对局人数的评估歌曲及正数权重，并设置参考时机波动和 1 或 3 组操作。每组操作使用相同的 120 种技能顺序，不额外漏击；这是参考发挥，AP／FC 标签不能确定 JUST 准度。

默认“舞台安排”通过 `artifact('projection/arena.json', { optional: true })` 读取与卡库、谱面相同的不可变内容快照，核对内容版本、账号区服和条件能力。`arena-stage-config.mjs` 显式解析 league → band、赛季与场次时间交集，使用 `[validFrom, validUntil)`；当前配置不唯一、过期缺后续或链接 ID 无效时不自动替换。入口可接收 `band`、`season`、`regulation`，未指定乐队时优先展示当前三段 JUST 乐队。场次选择弹窗按日期列出该赛季已发布时段，同时展示属性图标和有序的三段类型；可选择具体场次或跟随当前舞台，历史与预告标为试配。属性与三段任务进入既有计分视图，COMBO／LUCK／混段不开放 JUST 搜索。页面可见时每分钟、重新可见及开始计算前重新解析条件，轮换使旧结果失效。

“手动试配”固定为三段 JUST。属性 0 沿用原曲，99 表示 ALL；成员限定所选乐队，留影不限乐队。曲池是用户声明的评估范围，不推断歌曲所有权或模拟抽歌。权重默认等权，表示评估时各歌曲的重要程度；每首歌曲只出现一次，难度按 EASY、NORMAL、HARD、EXPERT 排列，在该行独立选择统一难度，修改难度保留歌曲权重。减少对局人数后若歌曲超限，保留原选曲并提示移除，修正前不计算。同一队伍的成员、留影、配对、队长及实际养成跨曲不变。

本版先按同曲同难度开展比较。对手仍以最终段落成绩的条件情景表示，没有从对手卡库、准度或另一难度推算成绩，不提供 HARD 为主／混合／EXPERT 为主的房间推荐。也不预设 EXPERT 一定比 HARD 得分高；选定难度后使用对应真实谱面。结果以 `poolMode=one_difficulty_per_song`、`weightMeaning=evaluation_importance` 标明曲池语义。

`arena-context.mjs` 为综合力、技能目标与任务奖励创建相同的歌曲视图，不修改原始规则。`arena-team-search.mjs` 使用既有配对求解器，生成综合力、JUST 成员／留影、转换与扩窗组合及队长起点。候选生成受这些搜索方式限制；最终排序使用整场分数，不以综合力或固定 JUST 权重替代。完整计分阶段遇到未支持技能时，整支候选退出比较并提示未参与比较的数量；生成阶段无法计算、缺失谱面或损坏输入终止任务，不能按剩余曲目重新归一化。

`gekisou-song-score.mjs` 的可选 `includeRankingSamples` 返回每次操作／技能顺序的音符分与三段计数、区间分、Perfect 数。`arena-comparison.mjs` 使用现有排名奖励表逐次取整，再比较对手未知时的名次范围，禁止用平均计数先算名次。同计数按区间分、Perfect 数比较，完全相同的结果必须同名次。

默认排序最小化**最大选错损失上界**：对每支候选，与另一支固定队伍比较，在同一组强弱关系允许的名次组合中取最大得分差；先按声明权重聚合整个曲池，再选最不利的替代队伍。这里允许不同段落、操作与技能顺序面对不同对手，且允许所有符合比较顺序的名次组合，属于宽范围压力测试，可能包含实际对手队伍无法同时实现的成绩。它不是真实对手分布、实际胜率或真实期望最优。排序及上界只针对本次完整候选集合；展示时切换对比对象不改变排名。

配队条件以舞台与曲池两栏排列，复用共享图标选项。场次选择、属性图标、三段任务及有效时间集中展示；“参考发挥”并入曲池标题旁，点击紧凑摘要打开浮层，点击外部或按 Escape 收起。乐队选择使用已有 `images/filter-bands` 圆形徽记，随代码资源打包，游戏素材继续置于忽略目录。乐队、属性、人数与难度选项按内容宽度排列。曲池按舞台乐队限定到有可计算谱面的歌曲，选歌面板支持封面、标题搜索和点击难度加入；舞台属性与任务覆盖原曲，不按原曲属性或任务筛掉歌曲。切换乐队移除不再适用的选曲并提示；已选歌曲以封面、行内彩色难度标签和权重编辑。评估曲池包含对手可能提交的歌曲，不以本人歌曲拥有状态过滤。推荐、取消、进度及修改条件放在底部窄幅固定操作栏，摘要和进度在左、紧凑按钮在右，收起设置后仍可操作；无效输入会展开对应设置。卡库与歌单保留共享悬浮入口，复用操作栏高度避让，设置内不再重复卡库管理。结果采用候选栏与当前队伍详情并排的布局；候选栏直接展示推荐队与当前情景最高分队（对手未知时为上限最高队）的成员／留影缩略图、队长及分数，选中项以浅色背景和“当前查看”文字标识。候选缩略图相对当前查看队伍标记差异：新成员／留影用“换”标记，队内留影重新搭配用“调”标记，更换队长单独突出。“换／调”使用卡图下方的独立标签，队长标在卡图上方，均不遮挡卡面；同一行卡图保持对齐。未变化的卡图淡化，并显示更换数量摘要。比较按成员角色对齐，整组调位不会误算为换卡；同一角色更换卡面仍视为更换成员卡。悬停可查看前后卡名，完整候选列表使用相同的差异标记。从完整候选面板选择其他方案后，该队也保留在候选栏，便于切回比较。对手未知时显示末位至第一的整场得分范围；固定名次及对手试算显示相对推荐队的分差。完整候选面板每页六队，默认按推荐顺序，也可切换为分数降序；对手未知时明确按得分上限排序，同分保留推荐先后。候选分数跟随固定名次或当前歌曲的对手试算条件。选择后一次展示一队，保留所选谱面、名次情景和已填对手计数；浏览排序不改变原推荐结果。队伍顶部默认“对手未知”，突出三段 JUST 计数与从三段末位到三段第一的得分范围，不指定或预测名次；推荐仍按对手计数变化下的最大损失排序。可切换三段第一、三段末位或输入对手计数试算名次。固定名次显示曲池加权参考分；对手试算显示当前所选歌曲分数。每次操作先独立排名、加上奖励再平均；若样本名次不同，显示最小至最大名次。手动对手使用输入 JUST 计数，段落分与 Perfect 数为 0，初始计数取推荐队与同名次高分队之间，均为可编辑的比较情景。

全队激奏汇总常显在队伍卡面上方，按计数、扩窗、转换、得分等作用分栏，窄屏自动分行；不再占用独立页签。详情区保留“队伍搭配／得分比较／逐曲数据”三个页签，默认展示五组配对及各卡技能，切换候选时保留当前页签，支持方向键和 Home／End 切换。五组成员／留影显示每张卡的实际等级技能、JUST／COMBO／LUCK 类型及计数、转换、扩窗、得分等作用；不属于本局任务的技能标为不触发。队伍沿用活动收益的五列配对形式，每列上方为成员、下方为留影，第三列顶端标出队长；窄屏改为每组两卡并排。卡面复用 `createTeamCardView`，显示属性、稀有度、乐队和实际等级／觉醒或突破；卡名与角色放在卡面下方，每张卡直接展示激奏类型、作用、等级和简短效果；按当前配对筛选乐队分支，不触发的任务仅保留类型与状态。摘要保留累计上限、入段 LIFE 条件、转换的计数目标与转换目标、单次额度及每段／整曲发动预算，原文通过共享技能浮层查看。没有完整摘要模板的条件组合沿用原文。推荐完成后收起条件并定位到结果区。桌面侧栏布局中，卡库与歌单悬浮入口横排放在底部操作栏右侧，避免遮住技能。宽屏候选栏随页面滚动保持可见，窄屏移至详情上方并排展示；当前队伍详情展示紧凑的整场得分与三段表现，三段名次与计数使用紧凑行，宽屏下情景切换与三个页签同排，窄屏自动分行，下方显示所选内容；曲池摘要收在队伍标题旁，不重复罗列选曲；宽屏得分与三段表现并排，窄屏分行。沿用站点颜色和字体变量。未计算时不展示装饰横幅；底部操作栏保留小问号“推荐原理”入口，点击打开简短说明弹窗，支持关闭按钮和 Escape。原文复用 `cardSkillRows`，卡片简述与全队汇总共用规则参数模板，遵循[技能语义契约](skill-semantics.md)，并复用激奏条件编译器筛选当前配对的乐队分支；只有触发、持续、条件及重置规则完全一致的可加算效果才合并数值，时限和 LIFE 分支分别保留。逐曲数据通过页签切换。队伍可保存到现有共享队伍库；只保存配队与实际养成，普通工具不会自动继承舞台覆盖条件。

所有运算在 Worker 中执行。候选生成复用现有配对器，计分复用 `createGekisouSongCalculator.calculateRankingSamples`，沿用完整逐帧计分但省去推荐不用的普通参考分和回放展示数据。完整队伍按设备预算分发到现有 `createCalculationWorkerPool` 的 1–4 个 Worker；每队仍计算整个曲池及全部 120 种技能顺序，结果按原候选顺序合并后统一排序。共享调度器按时间片让出执行权。编辑条件、养成变更、取消及离开页面终止旧任务；迟到消息不应用。结果身份绑定规则摘要、实际养成、舞台条件及配置来源身份、谱面摘要、权重、发挥及搜索版本，单曲计分身份也包含有效歌曲行。页面不保存可复用的分数缓存。

通用舞台视图和比较层使用三段任务数组；本版搜索显式拒绝 COMBO、LUCK 与混段，不提供假入口。后续扩展需要各自的候选生成与随机模型验证，不能仅修改页面标签。

离线验证入口：`node --test site/tests/arena-team.test.mjs site/tests/arena-stage-config.test.mjs`，覆盖计数价值、同分、先排名后汇总、固定队伍反例、属性覆盖、125 种名次组合的奖励重算及实际养成保留。真实对局与触屏输入不在离线验证范围内。

## 本次设计范围

以下保留独立信息查询页的设计；配队页已实现的配置读取与条件交接以上一节为准。独立信息页的导航、积分、奖励及刷新内容指针仍按下列设计推进。

| 本次包含 | 本次不展开 |
| --- | --- |
| 独立舞台信息页、导航入口、区服／赛季／乐队切换 | 固定队伍的多曲目标、搜索算法、候选生成和性能调优 |
| 当前属性、三段类型、有效时间与已公布轮换查询 | 改写计分引擎、普通技能机制和计算证明 |
| 段位门槛、基础 AP、奖励及参赛规则查询 | 真实胜率、完整 AP 预测、自动上分建议 |
| 配队入口承接页、条件摘要、跨页传参与失效提示 | 尚未接入计算器时提供伪可用的“开始计算” |
| 桌面／手机布局、加载／缺失／历史／过期状态 | 本轮接入账号登录、个人段位读取或真实对局 |
| 排行榜的状态位置及后续接入约束 | 未核验协议即采集榜单或展示模拟排名 |

首版满足三件事：用户能查清某乐队当前的舞台条件，能理解规则与基础积分，并能从同一上下文进入舞台配队入口。信息查询不依赖个人卡库、计分规则是否可用或玩家登录。

### 页面组织选择

| 方案 | 取舍 |
| --- | --- |
| 独立信息页＋薄配队承接页（采用） | 信息可独立发布；承接页只负责舞台条件与能力状态，后续复用既有配队器，不新建计分引擎 |
| 全部放进现有配队器的一个模式 | 查询规则也要进入复杂工具；未接入算法时容易误落到普通配队，不适合本次范围 |
| 为舞台新建完整门户与独立计算器 | 页面、卡库和计算逻辑重复，当前需求不需要 |

## 页面、导航与链接

以下为信息查询接入后的路由与交互设计，沿用站点现有区服／语言前缀。`/tools/arena/` 当前已提供上述手动 JUST 配队，其余入口与自动条件交接待实施。

| 页面／入口 | 路径与行为 |
| --- | --- |
| 激奏舞台信息页 | `/{region}/{locale}/arena/`；站点“活动”分组新增“激奏舞台”，排在活动总览之后 |
| 舞台配队承接页 | `/{region}/{locale}/tools/arena/`；使用现有工具页框架，显示当前条件、入口状态和返回信息页的链接 |
| 信息页主操作 | “舞台配队”；进入上述承接页，不进入匹配、不开始计算 |
| 工具目录快捷入口 | “舞台配队”；无有效舞台选择时先进入承接页选择条件，不能假定某乐队 |
| 原有配队器 | 后续以明确的舞台能力接入承接页；本次不改变普通／激奏模式的行为 |
| 玩家排行榜 | 首版在信息页显示可用状态；未接入时不建立空排行路由、不显示假榜单 |

`region` 是内容版本（现有 `global`／`jp`），`serverId` 是账号区服；两者不合并。现有 Global 的港澳台、韩服、EN 标识沿用 `game-servers.mjs`，语言不决定区服。Global 公共快照不能自动证明所有账号区服的开放时间相同；展示资料范围，未经确认的区服不启用当前舞台配队。

信息页支持 `server`、`season`、`band`、`regulation`、`view` 查询参数：

- `season=current` 为默认，运行时解析；明确的赛季 ID 可查看已发布资料，未收录的历史显示“该赛季资料未收录”。
- `band` 指乐队 ID；通过 league 映射找到规则，不把 `leagueId` 和 `bandId` 当成同一字段。
- `regulation` 只用于指定已公布条件的详情；它不能覆盖数据中的属性或三段类型。失效／未知 ID 显示提示并提供“查看当前条件”，不悄悄选另一期。
- `view` 为 `overview`／`ranks`／`rules`，对应页内内容区；桌面为页签，手机仍为三项页签，不额外套一层侧栏。
- 用户主动切换选择时更新 URL，浏览器前进／后退恢复选择。定时刷新和倒计时不产生历史记录。
- “复制页面链接”固化当前选中的赛季、乐队和规则 ID；同 ID 数据修订后显示最新发布内容及资料时间，不承诺该链接保存旧版快照。
- URL 不包含个人卡库、账号令牌或完整队伍；本次入口也不在后台写入已有队伍草稿。

初次进入优先使用有效链接参数，其次使用同区服上次选择；都没有时展示当前赛季的第一个可用乐队，并清楚高亮，用户可以立即切换。无当前赛季时展示状态及已收录赛季列表，不把最近一季冒充当前赛季。

用户主动切换乐队或赛季时，清除不属于新选择的 regulation 详情，回到新选择的概览；外部链接本身含不相容参数时则提示错误。自动轮换只更新“跟随当前”的视图；用户正在查看指定历史／预告详情时保持该详情，提供“查看当前条件”，不擅自跳转。

### 桌面结构

下面是信息层级示意，内容由当前查询决定，不是实时线上快照。

```text
站点导航 / 活动 / 激奏舞台
激奏舞台                            资料更新：…  [刷新资料] [复制链接]
```

### 段位与积分页签

上方展示当前乐队的段位梯级，默认按大段位折叠，展开可见小段位名与对应门槛。段位名、门槛及开放状态从表读取；没有个人数据时不放“我的段位”进度条，也不标记玩家当前所在档。

下方是“基础 AP 查询”：选择**赛前大段位**和对局人数（2～5），展示各名次对应的基础 AP。初始可展示表中第一个大段位及 5 人局，控件明确可修改，不使用“你的对局”。正负数保留符号，颜色只是辅助。缺少该组合时显示“当前资料没有此积分配置”，不能补零。

结果旁固定说明“基础 AP，不含道具及服务端其他修正”。道具、跨段、赛季重置及特殊结算只展示已确认规则，不给最终积分预测。AP 与尚未确认的总积分分类分别处理，不因协议字段出现而增加总榜。

### 奖励与规则页签

按用户问题分为“如何参赛”“奖励如何领取”“段位与赛季如何结算”三个内容组，默认展开参赛条件与奖励摘要，详细表格折叠。

- 参赛摘要：成员来自所选乐队、留影不限、提交自己拥有的该乐队歌曲、匹配后抽歌、抽歌后不能换队。
- 每日奖励：明确是所有乐队合计最多 3 次；显示重置时间，不显示未经账号读取的已领／剩余次数。
- 首次晋段：按所选乐队展示规则和已知奖励门槛；不推断个人是否已领取。
- 赛季奖励：解释按所有乐队中该赛季最高达到段位结算；不要误标成当前乐队独占奖励。
- 奖励物品仅在关联表与物品资料可解析时显示名称、图标、数量；缺少图标保留文字，缺少内容显示资料暂缺，不捏造奖品。
- 断线、处罚、继承规则以已确认帮助为依据；未还原部分明确写“具体调整规则待确认”，不把静态字段值当完整公式。

帮助文案与配置值分离：玩法解释可以随代码维护，次数、有效时间、段位门槛、基础 AP 和奖励数量随数据发布。文本内容通过安全文本节点渲染，不直接执行原始 Master 富文本。

## 信息数据契约与更新

### 数据生产与展示分离

采用现有内容发布链，新增经过白名单投影的 `projection/arena.json`，随同一内容 manifest 交付。浏览器通过已有 `artifact` 读取，不直接请求游戏接口、不接触解密密钥，也不把原始协议或私有证据发布到站点。未包含该文件的旧内容快照显示“舞台资料暂未提供”，不影响其他页面。

| 来源 | 投影内容与校验 |
| --- | --- |
| `MasterArenaSeason` | 赛季 ID、名称、开始／结束、统计截止，分别保留语义 |
| `MasterArenaLeague` | league ID、乐队 ID、名称、开放约束；显式建立 league → band 映射 |
| `MasterArenaLeagueRegulation` | league 引用、属性、三段类型、开始／结束；保留 0 回退与 99 ALL，不在信息层替换成某首歌的值 |
| `MasterArenaRank` | 乐队、段位层级、小段位、门槛、开放约束；未确认的重置字段不直接成为 UI 公式 |
| `MasterBattleLivePlace` | 赛前段位 × 人数 × 名次 → 基础 AP；缺项不补零，重复冲突拒绝该功能 |
| 每日／晋段／赛季奖励表、帮助与物品目录 | 已核验的显示字段及物品引用；未知关联只影响对应奖励区域 |

拟定投影外层字段：`schemaVersion`、`region`、`sourceReleaseId`、`observedAt`、`sourceRevision`、`serverScopes`、`timeZone`、`timeSemanticsVersion`、`capabilities`、`seasons`、`leagues`、`regulations`、`ranks`、`basePoints`、`rewards`。名称可按项目序列化风格落实，但以下语义必须保持：

- `sourceRevision` 绑定相关源表内容摘要；配置 ID 不变但内容变化时也更新。
- `serverScopes` 明确此资料覆盖哪些账号区服，未确认不填成“全部”；跨语言仅换文案，不改变数值身份。
- 时间转换由数据生产侧按已核验区服时区与端点精度执行，输出绝对时间；客户端不靠 `new Date(无时区文本)` 猜测。规范化区间使用 `[validFrom, validUntil)`，源数据如何映射必须有边界用例。
- regulation 本身没有直接赛季字段时，以时间与所选赛季求交集，不补造外键。同一 league 同时命中多个相互冲突的配置时，当前条件为不可用，不取数组第一条。
- 能力分别声明 `conditions`、`ranks`、`basePoints`、`rewards`、`rankings`；信息局部缺失不导致整页失败。实际计算能力还受代码版本与计分数据门槛约束，不能被一个内容布尔值直接打开。
- 对外只显示已经进入正常发布范围的资料；本机解包得到的未来表项不因“存在”就自动公开。本轮不新增未来内容公开策略。

当前时区／端点语义若尚未完成核验，可展示原始时间的说明性文字，但不能提供精确倒计时或标成可用的当前参赛上下文。完成确认后再打开相应能力；该缺口不阻止静态玩法说明页。

### 页面状态与新鲜度

信息状态与入口状态分开。页面固定在一份不可变内容快照，沿用 `runtime/content.mjs` 的规则，不热混合新舞台配置与旧目录。

| 情况 | 页面表现 | 可用操作 |
| --- | --- | --- |
| 首次加载 | 与真实布局等高的条件、安排占位；不出现假 ALL 或假任务 | 导航可用，入口等待解析 |
| 当前快照有唯一有效配置 | 显示条件、绝对有效时间和资料更新时间 | 查看各页签、安排、复制、进入承接页 |
| 已收录下一期且到达时间边界 | 用同一快照重新解析，更新状态与条件；相邻同值也更新所属时段 | 提示“舞台条件已更新”，不强迫页面滚回顶部 |
| 边界后没有新配置 | 旧条件保留为“上一期”；当前区显示“新条件尚未收录” | 刷新资料、查看规则；不继续按旧条件交接 |
| 已有数据但刷新失败／离线 | 显示“当前展示已保存资料，未能检查更新”及资料时间 | 允许查阅、复制；不宣称已确认最新，不进入可计算状态 |
| 内容版本或摘要校验失败 | 显示明确错误及重试 | 不使用未验证返回，不回退其他区服 |
| 段位／奖励局部缺失 | 对应页签内显示缺失原因，当前条件区仍可用 | 其他功能继续使用 |
| 无赛季或未开放 | 显示“当前没有已公布的舞台赛季”，可查已收录资料 | 不以空表暗示接口失败，不伪造倒计时 |

“刷新资料”检查当前内容指针；指针未变则更新本次检查状态，指针变化则显示“有新资料，重新载入”，重载整页后采用新快照。本次承接页没有可丢失的队伍编辑，能保留 URL 选择并重载；后续加入队伍编辑时再复用草稿保护。

仅在页面可见时每 5 分钟检查一次指针，手动刷新、重新聚焦和配置边界可额外触发；同一时刻合并重复请求，后台不轮询。5 分钟是首版前端检查频率，不改变既有内容生产调度，不承诺官方热更新会在 5 分钟内被收录。已发布的未来时段可以在本地边界自动切换；未发布时段只能显示缺失。

当前时间判断使用可注入时钟以便测试；默认设备时间，界面显示区服时区，不宣称已校准服务器时间。检测到设备时钟明显跳变时重新解析并提示检查时间。发起条件刷新与跨页承接都带请求代次，切乐队／赛季后的迟到响应不得覆盖新选择。

### 属性和三段类型如何覆盖

`ArenaLiveMusicData` 包装原 `MasterLiveMusic` 与舞台 regulation，按字段独立回退：

```text
有效属性 = regulation.musicType != 0 ? regulation.musicType : 原曲.musicType
有效任务[i] = regulation.mission[i] != 0 ? regulation.mission[i] : 原曲.mission[i]
```

`0` 表示回退；属性 `99` 是明确的 ALL，不能当成回退。三段分别处理，例如原曲为 COMBO／LUCK／JUST，覆盖为 JUST／0／COMBO，则实际为 JUST／LUCK／COMBO。有效属性同时用于 `MusicType`、`ParamMusicType`、`SkillTargetMusicType`。

歌曲 ID、谱面、音频、歌曲标签等仍来自原曲。覆盖歌曲属性不会修改卡片属性或乐队、留影配对关系，也不会把歌曲标签改成舞台属性。综合力仍分别处理歌曲属性匹配、歌曲标签匹配及卡片间的关系。

客户端加载谱面时把有效三段任务传入 `LiveMusicScore`。段落沿用原谱面 `FeverList` 的起止位置，按顺序赋予任务，最多取前三段；没有在该构造路径生成舞台专用时间轴。现有计算器要求恰好三个有效段落，缺失时应明确拒算，不能补造边界。

覆盖 getter 的 162 组、段落构造的 135 组原生离线检查通过。段落检查替代了集合、位置读取和音符区间读取，只证明边界对象及类型传递；不证明音符落在边界两侧时的完整调度、所有技能同帧顺序或网络确认时机均已验收。

### 计分与段位积分

新版音符计分核心的 4096 组离线向量与现有核心一致。已对照的音符参数、判定参数及窗口、连击加成、激奏排名奖励、LUCK 基础点数与抽选表，在基线覆盖字段上未变化。因此可以复用现有核心及三种任务模型，但不能据此宣布整个新版计分状态机已验证。

段落奖励仍按段落分数与排名奖励百分比计算。奖励表的组合分类取决于**覆盖后的完整三段类型**，必须重新选择；不能保留原曲的组合分类。段落任务计数决定排名比较，不能直接当作得分倍率。固定段落名次或假设对手时，输出都是相应情景下的估分，不能称为个人胜率。

### 固定队伍的多曲评估

评估单位是完整队伍 `T`：成员、留影、槽位配对、队长及养成假设固定。对曲池中的歌曲／难度 `s`，按同一舞台上下文和预先声明的发挥、技能顺序抽样、对手及随机假设得到 `score(T,s)`。

共享歌单的 `runPlaylistTeamBatch` 已能批量逐曲配队，但每首歌独立选择队伍，不能当作舞台固定队伍的联合目标。推荐舞台首版只做已保存候选队伍的比较，目标为声明权重下的平均分：

```text
value(T) = Σ weight(s) × score(T,s) / Σ weight(s)
选择 T* = argmax value(T)
```

现有 `evaluatePresetPool` 可复用矩阵生成思路；`selectPresetPortfolio(matrix, 1)` 的第一步已经等价于上述单队选择，`contributions.singleTeamScore` 也已给出每队加权均分。无需重写该数学逻辑，但入口、结果结构和多候选排名必须明确为固定队伍，不能沿用默认保留多队、逐曲选择最强队的组合展示。

反例：两首等权歌曲，A 得分为 120／60，B 为 100／100，C 为 60／120。固定队伍应选 B，均分 100；多队组合会在两首歌分别用 A、C，显示 120。这种组合收益在锁队舞台不能实现。现有函数的合成矩阵检查已复现该区别。

评估契约：

- 同一首歌的各候选使用相同玩家操作样本和随机种子策略，逐曲改变 `selectedSongId`／难度不改变队伍；技能顺序随机样本不能被误报为抽歌后允许重新编队。
- 曲池可选效率精选、用户常用或明确枚举的可能选曲。等权是默认比较假设；自定义权重需记录来源。相同歌曲／难度可以合并计算，但必须累加原提交项权重，不能先去重再等权。
- 每队输出逐曲分数、加权均分、覆盖曲目与缺失原因；段落计数和条件奖励单独显示。池内最低分、抽样最低分分别标明，不称为真实保底。
- 不同歌曲基准得分不同，平均绝对分会更重视高分曲。逐曲相对收益或最大遗憾可作为另一个明确目标，不能在同一排名中悄悄混用；首版不把它扩展为真实胜率或 AP 期望。
- 某队在某曲遇到不支持的技能、缺失谱面等情况时，标为不完整，不能删除该曲后重新归一化并与完整队伍直接排名。只有用户明确接受统一缩小曲池后，才对所有队伍重算。
- 未知对手提交分布、段落结果及服务端修正时，不展示真实抽歌期望、胜率或上分效率。三段第一与三段末位是可选的计分情景，不是名次预测；三段同类任务尤其需要展示名次敏感性。
- 候选只来自已保存队伍时，只保证候选集合内比较，不给全卡库最优证书。后续搜索必须面向整个曲池评价固定队伍，不能拼接逐曲最优队伍得分。

### 轮换、结果身份与缓存失效

离线探针仅在私有作用域覆盖歌曲行，24 组属性／三段类型得到不同综合力和分数，却返回同一单曲 `inputHash`。原因是 `createGekisouSongCalculator` 的结果摘要未直接纳入有效属性和任务。这个探针证明新增覆盖层不能沿用该身份契约；它不是现有线上舞台缓存串用的报告。`evaluatePresetPool` 外层已对规则整体取摘要，也不能代替单曲结果、worker 和页面的统一上下文。

接入时区分三类身份，字段名称可以随实现调整，但不能漏掉语义：

| 身份 | 必须包含的语义 | 用途 |
| --- | --- | --- |
| 舞台上下文 | 区服、业务模式、赛季、乐队、regulation 身份及内容摘要、区服时区、赛季与规则相交后的有效期 | 判断结果是否属于当前舞台、是否过期 |
| 单曲计算身份 | 上下文、有效歌曲属性与三段类型、源数据版本及摘要、计分模型版本、谱面内容摘要、完整队伍／养成、发挥样本、随机与技能顺序策略、对手／名次、确认延迟及精度 | 结果可复算，区分会影响数值的所有输入 |
| 多曲评估身份 | 单曲身份集合、规范化曲池与累加权重、候选集合、比较目标及版本 | 防止曲池或权重变化继续显示旧排序 |

处理规则：

1. 在开始计算和接收结果时都检查上下文。请求携带上下文摘要及请求代次；切乐队、换曲池、跨轮换或收到新配置后，取消旧任务或丢弃其迟到结果，不能覆盖新页面。
2. 有效期按区服时间及 Master 契约解析；明确源字段端点精度，再统一为内部区间。检查赛季与规则交集，不能套本机时区。若缺失或冲突，显示条件不可用，不沿用上一期作为当前期。
3. 轮换定时、页面重新聚焦／恢复、数据刷新时重新解析。时间过期不依赖用户手动刷新；数据修订也不依赖日期或 ID 改变。同 ID 的属性、任务或有效期热更新必须触发重新判断。
4. 旧结果可保留用于历史查看，但标为过期，并显示对应条件；新结果完成前不冒充当前推荐。存档队伍保留，成绩及推荐需重算或重新验证。
5. 若相邻区间数值相同，仍更新当前上下文身份。可以另以完整数值依赖摘要复用计算内核结果，但必须重验证、重新封装当前有效期，不能直接把旧结果标为当前。
6. 原始谱面解析可按内容摘要复用；综合力、技能筛选、任务组合奖励及成品结果均受覆盖影响。不能原地修改规则对象后继续使用旧 calculator 闭包或其内部缓存。
7. 个人养成、规则表、技能支持范围、模型或谱面更新同样使相关结果失效。只变曲池权重时允许复用仍有效的单曲矩阵，但必须重新聚合并生成新的评估身份。

验收至少覆盖：只改属性、只改某一段类型、`0` 回退与 `99` ALL、相邻期同值、同 ID 热修、赛季交界、跨期迟到 worker、切乐队、后台恢复、离线缺配置、权重改变和养成更新。验收应同时检查分数、摘要、有效期与页面状态。
